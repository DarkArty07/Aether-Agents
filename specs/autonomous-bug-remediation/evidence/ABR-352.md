## Diagnosis

The issue report records one `_queue.Empty` from `results.get(timeout=10)` during a full
canonical run, followed by an immediate passing targeted rerun. On the verified unchanged
Aether source, the old fixture was run directly and repeatedly without reproducing a missing
commit or a CAS invariant failure:

- Unchanged targeted wrapper run: `1 passed in 0.60s`.
- Unchanged targeted wrapper repeated 20 times with `HERMES_TEST_FILE_RETRIES=0`: 20 passed,
  0 failed; wrapper elapsed time was at most 0.878s per run.
- Unchanged lifecycle-module wrapper run: 90 passed in 284.79s.

The reported failure is therefore a bounded fixture/environment timeout observation, not a
reproduced product defect. The old test released its common start event immediately after
calling `Process.start()` for both children; it did not establish that either spawned child had
reached the intended contention gate before the release. That admission race is test ordering,
not evidence that the lifecycle lock lost a commit.

## Bounded candidate change

Commit `d5b69dd` makes the interleaving explicit:

1. Each spawned contender constructs its `ReleaseStore` and signals a per-process ready event.
2. The parent waits for both ready events before setting the common release event.
3. The existing 10-second result and join deadlines remain unchanged.
4. The existing assertions remain unchanged: exactly one `committed`, exactly one `stale`, one
   final active release, one committed journal, and one `ACTIVE_RELEASE_CAS_MISMATCH` journal.
5. A failure cleanup path releases the gate and terminates only a still-running fixture child;
   it does not change product behavior or test expectations.

No sleeps, retries, deadline increases, assertion weakening, product synchronization changes,
or journal-storage edits were introduced.
