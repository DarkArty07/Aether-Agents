## Why a separate entry skill rather than another contract method

Owner clarification: `/plan` is the owner-facing start/end and continuity record for the entire project-local objective, including expected delegations; an unlimited number of justified Objective Contracts may be needed. The contract, not the plan, delegates work. R2-FR-204b–e and `objective-contract-design` already describe the planning method, but `docs/guides/objective-plans.md` currently calls the Hermes `/plan` generic and does not make the explicit slash invocation reproducible. A short Aether-owned `plan` skill for Morfeo is the non-overlapping entry; it references the existing canonical method rather than adopting the generic microtask/TDD/commit/delegation recipe. A Project Canonical Skill would have to be copied into every project and would not become a native profile slash command. A global Hermes core patch is not justified on the selected fork.

**Spec Kit checked at exact current inspected revision:** `github/spec-kit` `5cc1f2a846c4c296adb45f46b72a9a0bc13883a7`, `templates/commands/plan.md:66-71,108-110,137-159`. Its plan command creates a feature's technical research, model/interfaces and quickstart, ending before tasks. Aether retains that technical `specs/.../plan.md` role; an Objective Plan is different: one local cross-session route for an owner's objective and potentially several contracts. R2's research artifact records the corresponding deviation; no Spec Kit code is vendored.

## Native slash and distribution feasibility

In the selected maintained fork, `hermes_cli/commands.py` does not register `plan`, while `agent/skill_commands.py:402-495` scans native `SKILL.md` files and registers a noncolliding skill frontmatter `name: plan` as `/plan`, deduplicating names. Root `skills/plan` and an existing nested learned `plan` may coexist; runtime readback of which one wins is mandatory. Public Hermes documentation describes a newer built-in `/plan`, but that is not the selected fork; a future selected upgrade must requalify this interface, not silently use the built-in.

Aether `src/aether_agents/lifecycle.py:895,4412-4456,4484,4711,4827,4913,5025,5629-5678,5857-5906` currently treats canonical skills as one all-role inventory. `profile-bundle.json` schema 2 already has a separate skill map per role, but generation and validation require the same fixed set for all three. Wheel/sdist and native activation tests (`tests/test_observation_packaging.py`, `tests/test_observation_lifecycle.py`) bind the exact current set. The chosen change is a strict **per-role, per-authenticated-release** inventory, not a second loader or a loose manifest-driven allow-all.

A material prior-version obstacle is confirmed by source inspection: the executing manager's `_wheel_profile_bundle_sha256` refuses additional wheel resources; simply adding `skills/plan/SKILL.md` to a wheel would fail its exact-set check. This is a **known limit for a future local update**, not a reason to qualify a bridge or rollback before merging source. The owner corrected Morfeo's initial scope: deliver the canonical skill, documentation and reviewed source in `main` without touching active sessions; no release or activation was requested. Candidate bundle/native loading and integrity checks remain necessary, and the update path must be reported as unqualified rather than claimed safe. Already-authored reader compatibility code may remain if reviewed and green, but do not expand the merge gate into old→bridge→new, compensation and rollback. Those claims belong to a separately authorized release/update objective, if one is ever requested.

## Rejected shortcuts and change impact

- Adding `plan` to the flat `_CANONICAL_SKILLS` list: installs it into Supervisor and Implementer and makes old manifests fail under the current constant comparison.
- Rewriting the private skill verbatim into the package: private assumptions/provenance and duplicate-name state are not vetted; promotion requires sanitization and independent review.
- Calling `git merge` a release: installed profiles match immutable release bundles and are not changed by source integration; no live restart, publication or deployment follows from this source objective.
- Disabling profile drift/ownership checks or editing an active home: makes a broken migration appear green and risks concurrent sessions.

Impacted owning artifacts: R2 §3.1 (explicit plan intent), the new objective [spec.md](spec.md), this evidence, `docs/guides/objective-plans.md` and related current-build guidance after implementation, focused candidate packaging tests and capability status. `DESIGN.md` three-role authority and existing `aether init` project behavior stay unchanged. Stop/replan if selected-runtime dispatch or exact Project binding is not supportable without an unapproved external effect; historical release qualification is a documented separate question, not an acceptance precondition here.
