# HLP-554 — Codex message-id prefix guard (maintained fork)

**Issue:** [#554](https://github.com/DarkArty07/Aether-Agents/issues/554), with the
#560 doctor finding that the installed RC17 runtime carried this guard as a live edit.
**Producer:** the owner-directed RC19 release and its RC18 adoption bridge (#564), 2026-10-03.

## 1. Defect and repair

Codex Responses rejects an assistant `input[].id` that does not start with `msg`. A
foreign id, such as a UUID minted by another provider, still passed the maintained
fork's only checks (nonempty and at most 64 characters) in
`_chat_messages_to_responses_input` and `_preflight_codex_input_items`. The result was a
non-retryable HTTP 400 that repeated on every later turn of an affinity-bound worker
session. The id is optional replay metadata, not a tool `call_id`, a credential or an
authority marker.

The repair keeps the id only when it also starts with `msg`. Content, phase, valid
`msg` ids and tool-call pairing are unchanged, and GitHub Responses still drops every
id. It is byte-identical to the two-condition guard that had been applied locally to
the installed RC17 `hermes-source/agent/codex_responses_adapter.py`.

  `agent/codex_responses_adapter.py` has the same length-only guard (`UPSTREAM_MISSING`

- Retire only after adopting an exact upstream release whose guard covers the Responses
  issuers Aether uses, with these six cases passing without HLP-554.
