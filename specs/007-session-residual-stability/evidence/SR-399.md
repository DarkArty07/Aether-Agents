## 1. Context and Problem Statement

When the maintained Hermes fork introduces a new top-level Python module (such as `hermes_state_compaction` introduced in HLP-382), editable PEP 660 installs (`__editable___*` finder and `.pth` files generated by setuptools in `site-packages`) do not automatically discover the new module until an explicit editable reinstall is executed. In a runtime with multiple provisioned interpreters, partial or failed updates leave editable mappings out of sync across interpreters.

Unit U399 provides one authoritative, package-owned operation in new/disjoint files that reconciles editable Hermes mappings transactionally across every provisioned interpreter, captures private backups, executes forced offline/local reinstalls, verifies module origins with `env -i` / `python -I` canaries, rolls back all metadata atomically if any interpreter fails, and returns a structured receipt carrying source and metadata fingerprints.

Round-1 review (2026-09-11) additionally established that the operation must never mutate a target whose installed distribution is not editable: a clean release installation (or a missing distribution) is refused before any mutation with `NonEditableTargetError` and a receipt. That preserves the contract boundary that clean release installation stays strict and separate from this authorized dirty-runtime reconciliation. See §8 for the delta.

- **Live-run pre-condition (verified read-only at the candidate revision).** Both provisioned interpreters carry editable `hermes-agent` installs, so the operation's pre-flight accepts them:
  - `home/.venv-hermes/bin/python` and `home/.venv-hermes/src/hermes-agent/.venv/bin/python`;
  - each site-packages contains `__editable___hermes_agent_0_20_1_finder.py`, `__editable__.hermes_agent-0.20.1.pth` and `hermes_agent-0.20.1.dist-info`, whose `direct_url.json` is `{"url": "file://<project-home>/.venv-hermes/src/hermes-agent", "dir_info": {"editable": true}}`;
  - `inspect_editable_target(...)` (read-only preview of the pre-flight) returns `is_editable=True`, version `0.20.1`, 13 metadata files fingerprinted, for both interpreters.

  No live runtime state was mutated by this unit; the check imported the module from the unit worktree and only read site-packages and executed `-I` introspection queries.
- **Compatibility Impact:** `none` (new module and tests are entirely additive in disjoint files; no existing interface or behavior modified; the deferred wiring surfaces are not yet touched).
- **Residual Risk:**
  1. **Auto-discovery false positive on real forks.** With no explicit `intentional_modules`, `check_fork_packaging_inventory(<maintained fork>)` reports `('mini_swe_runner',)` in `missing_from_py_modules` because `mini_swe_runner.py` ships at the fork root but is undeclared in `tool.setuptools.py-modules`; the same call with the declared list is coherent. Any future caller must pass the explicit intentional-module list (or accept the false positive). Reproduced read-only against the maintained fork; the unit's own test exercises the intended behavior on disposable forks.
  2. **Unscoped build-debris removal.** `remove_editable_build_debris` deletes every top-level `*.egg-info` directory in the source root, not only the reconciled distribution's, and `get_git_status` plus `compute_source_tree_sha256` ignore `.egg-info` content, so a tracked directory of that name would be removed without surfacing in the preservation comparison. The maintained fork's `hermes_agent.egg-info` is untracked build debris.
  3. **Canary import breadth.** The default `verify_imports=True` imports every declared top-level module (including `cli`, `hermes_bootstrap`, `run_agent`) in a bare `env -i` subprocess. INT should confirm that is side-effect-free on the maintained fork before the live run; passing `verify_imports=False` limits the canary to resolution/origin checks if it is not.
