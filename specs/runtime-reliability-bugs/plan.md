## B267: extend and actually use the existing laboratory boundary

Owning Aether code: `src/aether_agents/lab/runner.py:368-393` (`isolated_hermes_env`), current live-run caller around 2139, and `src/aether_agents/lab/observation.py` around 498. Existing tests: `tests/test_e2e_harness.py` around 233-355. This is source mapping, not a mandate to split each file into a task.

Existing helper copies `os.environ`, drops `HERMES_KANBAN_*`, `HERMES_SESSION_*`, `TERMINAL_CWD`, `HERMES_CWD`, then pins home/DB/workspaces/XDG to a run root. A source-extracted pure probe with synthetic environment confirmed three leaked identities: `HERMES_DELEGATED_CHILD_CONTEXT`, `HERMES_PROJECT_ID`, `HERMES_TENANT`; it performed no DB access. Add those explicit names plus `AETHER_PROJECT_ID` to the existing removal set. The observation caller intentionally rebinds its own Aether Project after the helper; preserve this ordering. Do not strip all environment indiscriminately or remove unrelated permitted settings.

Use the helper at executable disposable-probe entry boundaries before module-level path caching. Resolve the final DB and workspace roots, including symlink resolution, and fail before writes if they escape the owned sandbox. Keep this preflight in the laboratory boundary, not the global production resolver. Direct read-only inspection of an unrelated board is not converted into a new prohibition. The native lab child receives explicit sandbox destinations and only its own identity. Regression must include poisoned environment, a witness DB separate from the lab root, caller coverage and parent-environment immutability. No live board is a test fixture. No cleanup of historical contaminated cards is authorized.

## B304: transcript fast path with read-only durable completion recovery

Fork owners: `agent/kanban_stop.py`, call seam `agent/conversation_loop.py` around 7880; native DB readers in `hermes_cli/kanban_db.py`; completion fence in `tools/kanban_tools.py`. Source-extracted assessor checks demonstrated full transcript=VALID, lost call/result=MISSING, wrong run=MISSING. These were synthetic structure probes only, not full DB qualification.

Keep `assess_kanban_handoff()` transcript behavior; `CONFLICT` must not be upgraded by fallback. On `MISSING`, `evaluate_kanban_stop()` can use one internal read-only durable resolver. Capture expected task/run from the actual worker context, independent of a task's current pointer after completion. Resolve only that worker's pinned DB or unambiguous explicit board; never fall back to current/default. Open SQLite in read-only mode using the existing read facilities where they support it; do not run the normal write-capable schema/bootstrap initializer just to validate a stop. Missing/unreadable/corrupt/ambiguous state is a failed proof.

The proof requires one consistent read snapshot with: task ID equal expected task; run ID equal expected run and its task equal expected task; task status `done` and `current_run_id` absent; run status `done`, outcome `completed`, non-null end time; native completed event matching this task/run. Use existing event names and semantics, inspecting their actual payloads; do not count a paired flow-notification event as a second transition or accept an unrelated terminal event. The native `completed` transition is the authoritative effect. If the card was reclaimed/reopened into a newer run, do not accept the old run. Do not fabricate an `ok` tool transcript to appease the guard.

Valid proof returns ALLOW with a truthful existing-durable-completion reason and no writes. Failed proof retains bounded stop-budget/error handling; avoid misleading claims of `running` without evidence. Do not weaken `complete_task(expected_run_id=...)`, mutate DB schema, reopen cards or repeat completion. Preserve existing block/review/request-changes semantics; they are not newly inferred from this completion-only recovery. Negative cases include board mismatch, wrong run/task/event, conflicting transcript, DB unreadable, task reopened, and repeated reads with unchanged DB/event counts.

## B295: bounded exhaustion classification, then configured failover

Fork owner: `agent/error_classifier.py`, `_classify_by_status`, current generic 503/529 branch around 1308-1325. It currently handles known overflow/empty-response patterns then returns retryable overload without `should_fallback`. The caller must also be exercised; classification flags alone do not prove a provider change.

Recognize the actually reported `503` body phrase `no available Codex accounts` case-insensitively and in bounded error text, after preserving existing more specific overflow handling and before generic overload. If the received protocol already supplies an unambiguous structured pool-exhaustion code, that may be matched without adding a router protocol. Do not generalize to generic `unavailable`, `catalog unavailable`, all 503s or all 529s: those are not proof of the reported permanent pool condition. Add other variants only with actual equivalent response evidence, not model guesses.

For this exhausted case set `should_fallback=True`, avoid same-route retry exhaustion, and keep existing reason/status compatibility where possible. Preserve transient overload backoff. Trace the branch's existing caller so only explicitly configured/authorized candidates are eligible for this exhaustion route; a fallthrough to auto-discovered payment/provider candidates is not allowed. Reuse the existing configured chain; no new routing framework, model selection, credential refresh behavior or arbitrary quota probing. Exhaustion without an eligible candidate ends as a clear bounded error. Keep current partial-stream/tool-effect protections; tests include an already executed benign local tool sentinel to prevent replay.

## B292/B301: one coherent auxiliary request path

Hotspot: fork `agent/auxiliary_client.py` is shared by named resolution, header forwarding and configured fallback. Supervisor should avoid competing overlapping edits; grouping or ordering ownership is decomposition freedom, not another architecture decision.

### Named resolution

Current evidence contradicts the simplistic prefix-loss diagnosis: `_try_configured_fallback_chain` retains the entry provider (around 5529), `_resolve_fallback_entry` passes it (5619), `resolve_provider_client` saves `original_provider` (6117), and named resolution checks it before the normalized form (6465). `hermes_cli/runtime_provider.py` and `hermes_cli/providers.py` support named aliases. Do not rewrite normalization just because it strips a prefix.

Qualify temporary `providers`/supported named-entry configuration with two distinguishable synthetic credential values, a bare model and explicit api mode. Drive direct resolution and a failing primary followed by the configured entry through real imports and loopback HTTP. Test both admitted name spellings, anonymous/built-in preservation, and absence of unrelated global credential selection. If these pass unchanged, add meaningful integrated regression coverage and record already-working evidence; no product code patch. Only a demonstrated same-path loss authorizes a narrow resolver repair. New resolver schema, a new alias convention or a different protocol is a design return.

### Header forwarding

The immutable upstream `agent/auxiliary_client.py:1367-1370` copies a non-empty dict `kwargs['extra_headers']` into `resp_kwargs`; the maintained fork's `_CodexCompletionsAdapter.create` builds `resp_kwargs` around 1514 without copying it. Port that small behavior, preserving authorship/source citation, not the surrounding refactor.

The fallback call helpers (sync around 5019, invocation around 9836) do not explicitly accept `extra_headers`. Trace both sync and async callers and carry a fresh copy of safe request-scoped metadata through each retry/candidate call. Internal parameter naming is local freedom. Do not blindly copy primary client default headers or request auth into a new provider. Use the existing destination-auth resolver and header helpers. Exclude Authorization, Proxy-Authorization, Cookie and provider-specific API-key/auth metadata from cross-destination forwarding; retain destination-generated values. Prefer carrying the existing known auxiliary attribution mapping before it is merged with destination authentication over inventing a permissive universal cross-provider header filter. If the current code cannot separate arbitrary provider-sensitive headers safely, return that material case rather than widening forwarding. Same-destination adapter semantics remain compatible.

Acceptance exercises actual HTTP requests for sync/async and streaming/non-streaming where supported, primary retry and configured fallback. A recording endpoint checks safe operation attribution, independent mapping copies, no stale headers on subsequent requests, and the secondary's distinct fake auth. No fixture model output is called a live LLM response.

## B294: cause-qualified lifecycle change, not speculative isolation

Fork owners: `agent/background_review.py` (new `AIAgent` around 812; shared cache session ID around 889; no persistence/session finalization around 843-907; parent-child registration around 909), `agent/conversation_loop.py` (cancel pending review at new-turn entry around 1687), and `run_agent.py` interrupt/close paths. The API loop can log `interrupt_abort` on bg-review while aborting that review's own request. Shared session ID does not prove shared HTTP client/interrupt flag.

First implement only tests/controlled harness instrumentation sufficient to distinguish parent/review instance, request identity and cancellation initiator. Prefer spies at existing seams to permanent telemetry. A real local HTTP server with event-controlled blocking allows the ordinary agent/request path to run without paid models. Qualify all B294 interleavings and intentional /stop with cache/session preservation. The harness must prove that cancellation of the review leaves the foreground client, flags and result intact.

Only if these reproduce the scoped race, adapt immutable upstream `_BackgroundReviewRun`, prepare/admit/cancel/finish behavior around `agent/background_review.py:914-1136`: reserve run identity before Thread.start, atomically deny admission after cancellation, track cancellation separately from foreground, and clean references only when they still name that run. Keep parent-to-review intentional stop propagation and nonblocking foreground progress. Do not detach review from all intentional stop handling, disable the feature, add a user setting, alter session ID/cache policy, or port unrelated review refactors.

If all controls already pass, record not-reproduced evidence and retain #294 open; do not claim the old incident was corrected. If a different demonstrated interruption cause appears, capture it and return that material design question to Morfeo while independent in-scope units may continue. Do not spend iterations on general log archaeology or a different lease/storage defect already owned by another issue.

Do not weaken gates because #323/#329/#349/#352 exist. Reproduce a failure on the unchanged relevant baseline, report it, and do not absorb unrelated repairs.

Rollback before activation is normal revert of this objective's source commits, never an old DB restoration or broad runtime reset.
