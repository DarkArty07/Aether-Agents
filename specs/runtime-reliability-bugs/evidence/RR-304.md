## 3. Implementation Mechanism

When `assess_kanban_handoff(messages)` evaluates transcript history:
1. `HandoffStatus.VALID` returns `StopAction.ALLOW`.
2. `HandoffStatus.CONFLICT` returns `StopAction.VIOLATION` (fail-closed, never upgraded by fallback).
3. `HandoffStatus.MISSING` invokes read-only durable recovery via `_verify_durable_completion`:
   - Resolves only the pinned worker DB (`HERMES_KANBAN_DB` env or explicit `db_path`, or `HERMES_KANBAN_BOARD` env or explicit `board`). Never falls back to `current` symlink or `default` board.
   - Opens SQLite strictly read-only with URI `mode=ro`, without running write-capable schema init, migrations, locks, or WAL write checkpoints.
   - Executes proof reads wrapped inside an explicit read transaction (`BEGIN` ... `ROLLBACK`/close) ensuring that all queries observe a single consistent read snapshot:
     - Task exists, `id == expected_task`, `status == 'done'`, and `current_run_id IS NULL`.
     - Run exists, `id == expected_run`, `task_id == expected_task`, `status == 'done'`, `outcome == 'completed'`, and `ended_at` is non-null.
     - `MAX(id)` for the task in `task_runs` does not exceed `expected_run` (rejecting reopened or reclaimed runs).
     - Native completed event (`kind IN ('completed', 'flow_terminal')`) matching `task_id` and `run_id` is exactly 1.
     - Conflicting terminal events (`blocked`, `changes_requested`, `review_requested`, `crashed`, `timed_out`, `gave_up`) for the run are 0. Paired notification events (`origin_signal`, `suspected_hallucinated_references`) are not counted as transitions.
   - If verified: returns `StopAction.ALLOW` with a truthful existing-durable-completion reason, `decision.nudge is None`, and zero database writes. The transcript assessment is preserved truthfully as `MISSING` rather than fabricating a synthetic `kanban_complete` VALID receipt.
   - If proof fails or is unreadable: falls through to bounded retry budget handling (`attempts >= max_attempts` yields `StopAction.VIOLATION`, otherwise `StopAction.NUDGE`).
