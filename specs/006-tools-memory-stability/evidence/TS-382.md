Sample size, and two distinct residual timing effects (measured, not hidden):

| Run group | Runs | Green | Failure mode observed |
|---|---|---|---|
| Base `266e412f` (pre-fix) | 2 | 0 | deterministic RED: legacy holds 2.185 s / 7.356 s vs 1.0 s budget; append raises |
| Candidate, same publication code as committed (before the malformed-marker handling fix) | 22 | 20 | append exhausted the fixture's **single** `BEGIN IMMEDIATE` attempt (1.0 s) while the publisher was between batches |
| Candidate `c13ff2b9b6` (committed) | 15 | 14 | one host-level I/O stall (see below) |

Effect 1 — SQLite busy-handler probing vs a 10 ms window: a dedicated timeline
diagnostic (`diag_concurrency.py`, temp DB, output retained) shows the publisher holding
the lock in ~0.17 s transactions with **7 lock-free windows of ~10 ms inside the
append's 1.011 s wait** and a max hold of 0.164 s. The fixture's appender gets exactly
one `BEGIN IMMEDIATE` attempt because its connection timeout equals its patience, and
SQLite's default busy handler sleeps in 50–100 ms steps by then — so it can miss those
windows. The fixture budget is 1/20 of the product routine budget (`_WRITE_PATIENCE_S =
20.0`) and 1/60 of the transcript budget (`_TRANSCRIPT_WRITE_PATIENCE_S = 60.0`), where
the same retry loop gets many attempts across the same batch boundaries. **The recorded
10 ms yield and the batch limits were left exactly as designed**; if the oracle must be
reliably green at its scaled budget, that is a Morfeo constant decision, not an
implementer one.

Effect 2 — intermittent host I/O stall: in 1 of 54 instrumented publications one staging
batch's *transaction body* took 7.873 s of the call's 7.875 s (~60 ms/row instead of
~1 ms/row, transaction count still 21), and the oracle's budget test recorded one 1.868 s
call the same way. Both are consistent with a disk/scheduling stall on this host: the
publication makes no data-dependent decision that could occasionally cost 14–60× more
work, the same fixture is rebuilt identically every run, and 30/30 isolated repetitions
show 0.121–0.165 s. Pre-fix, a stall of that class extended a transaction that already
held the lock for the whole transcript; now it is bounded to one batch.

## 6. Limits and residual risk

1. **Fixture-scale timing effects in the oracle** (§3): effect 1 (SQLite's busy handler
   probing 10 ms windows) accounts for the two earlier candidate failures; effect 2 (a
   host I/O stall) for one later failure. Measurement, not a long publication
   transaction, is the basis for both attributions, and no recorded constant was altered
   to hide either. If the oracle is required to be green on *every* run at its scaled
   budget, the 10 ms yield needs a Morfeo decision; at product budgets the same window is
   probed many times because the appender retries for 20 s / 60 s.
2. **A scoped runtime canary after adoption is not part of this unit’s evidence** — it is
   terminal-card work (`t_e4ba4b4e`) and remains **pending**; this unit claims no runtime
   acceptance, no adoption and no release conclusion.
3. **Snapshot capture for native callers**: the in-place compaction and prune callers
   compute their replacement from in-memory history and hold no persisted-prefix
   snapshot, so the writer captures it at method entry (D2’s explicit fallback). The
   capability (`snapshot=`/`capture_publication_snapshot`) is implemented and
   feature-detected for callers that later can supply one; forcing a caller-side capture
   would have required adding a DB read before every eligible prune, i.e. a wider caller
   rewrite that D7 rules out.
4. **`_assert_copy_columns_known`** fails a publication rather than relocating rows
   through an unknown column set: a future `messages` column makes the relocation path
   refuse safely (this guard caught the missing `compacted` column during development).
5. The `messages` table’s `compacted` value is preserved on relocated copies; the
   historical soft-archive marking of *originals* is unchanged.
6. Divergence from the maintained fork’s editable runtime tree was not re-verified here;
   adoption/hash comparison belongs to the integration and terminal cards.
7. Live-DB, VACUUM/migration/backup, issue #382, push/PR and PR ledger edits: untouched.
