## Problem and observable outcome

A successful auxiliary Codex/Responses call can report `output_tokens_details.reasoning_tokens` in its usage, yet `_CodexCompletionsAdapter` reconstructs only three flat token counts. The validated response and its one disposable `session_model_usage` row then show zero reasoning even when the provider supplied it. The original live discrepancy and closure conditions are in Issue #433; the later synthetic RED in the program's local Objective Plan is diagnostic only, not a GREEN test. The source fix preserves the reported reasoning subcount from the *completed response's usage* through the existing chat-compatible response, `_validate_llm_response`, `record_aux_usage`, `normalize_usage` and the existing SessionDB bucket, without adding that subcount a second time to output or total.

The loss is `agent/auxiliary_client.py:2077-2086`; the adapter returns `usage` at `:2138-2145`. The existing accounting chokepoint is `agent/auxiliary_client.py:8944-8994`, `agent/aux_accounting.py:71-138`, and `agent/usage_pricing.py:1381-1397` already recognizes both `output_tokens_details.reasoning_tokens` and the Chat spelling. These paths/lines describe the inspected revision, not immutable patch locations.

## Decided boundary and local freedom

1. **Response interface.** The adapted response keeps its existing `choices`, status, model and `usage.prompt_tokens`, `completion_tokens`, `total_tokens`. When terminal provider usage includes `output_tokens_details.reasoning_tokens`, the chat-compatible `usage` must expose that detail in a shape already read by `normalize_usage` (prefer `output_tokens_details`, which is already recognized). Object and mapping representations of the *provider usage and detail* must work where the adapter already accepts them. Do not infer reasoning from visible text, subtract it from output, change totals, emit an extra request/row, or replace the provider's report with an estimate. A missing detail remains absent/zero under the existing normalization contract; explicit zero stays zero. A defensive extraction of the nested detail within this adapter is locally discretionary if it preserves these invariants. Do not redesign pricing, SessionDB, or all auxiliary clients to solve a one-boundary loss.
2. **Terminal and fallback behavior.** The same rule applies whether `stream=True` yields a completed object or a `response.completed` SSE stream with terminal usage. Existing incomplete/failed/cancelled handling, output-text fallback, tool-choice, validation and Chat-provider fallback remain intact; a missing usage object must not fabricate accounting or make the call fail. Only a successful accounted auxiliary task with an existing accounting context produces a row. Treat malformed or conflicting detail as an oracle question to resolve against the existing normalizer semantics, not as license to double-count or add a new public error.
3. **Source/provenance separation.** The fork fix starts from an authenticated clean `aether-main` base and receives independent review. Reconcile its exact fork commit/tree, portable `HLP-433` patch artifact, SHA-256, rollback to the previous fork revision, `AETHER_FORK.md` record and upstream-retirement gate in Aether's `HERMES_LOCAL_PATCHES.md`, reconciliation entry/aggregate, patch manifest and tests. Follow existing HLP-428 patterns for *procedure*, not its substantive behavior. The source-only row must not assert `ACTIVE_LOCAL`/installed behavior before a separately authorized managed update. The patch is audit/reconstruction evidence, not an instruction to replay it onto the active runtime.
4. **Preserve #494's fixed historical source.** `AGENTS.md:17` and `HERMES_LOCAL_PATCHES.md:287-298` identify the reviewed #494 source as fork `58f8c37a…`; the separately owned, unmerged #494 release design may qualify that exact source even if #433 later advances `aether-main`. Keep an exact clean checkout of that commit available for #494; neither move #494's candidate lock to the new fork tip nor claim #433 is part of its rc9 canary. Merge this source fix independently only after checking both repos' current branch/PR status. If a concurrent change overlaps the adapter or the fork pin disappears, stop for reconciliation rather than silently rebasing acceptance.

The owner retains scope, activation and closure authority. Morfeo fixes the shared behavioral and provenance boundaries above; Supervisor independently checks the incoming contract, decomposes review/integration and owns normal closeout; Implementer chooses the minimal reversible internal helper and tests. No live provider call, model invocation, gateway restart, profile edit, tag, `aether update`, or Issue closure belongs to this source phase.
