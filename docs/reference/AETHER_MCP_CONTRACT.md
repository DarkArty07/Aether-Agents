# Aether MCP Tool Contract

> **Status:** `v1alpha2` SCHEMAS/RESTRICTED FOUNDATION IMPLEMENTED; PROVIDER ORCHESTRATION BLOCKED; ZERO TOOLS CALLABLE
> **Date:** 2026-08-08
> **Protocol:** `aether.mcp/v1alpha2`
> **Server namespace:** `aether` (`mcp__aether__*` in Hermes)
> **Authority:** ADR-0001 and `../architecture/AETHER_MCP.md`
> **Closed implementation scope:** bounded R0-R6 default-off redesign and qualification

## 1. Contract rules

1. The primary Hermes coordinator is the only full-surface principal.
2. Principal identity is derived from launch/session context, never trusted from
   an arbitrary request field.
3. All mutations require `operation_id`, structured `reason`, and expected
   effect class. They also require `project_id` except initial `project_admit`,
   whose project ID is generated by the server after identity verification.
4. The server generates event IDs, UTC timestamps, sequence, and integrity data.
5. No tool accepts a shell command string.
6. Orca provider responses must be structured; terminal prose is diagnostic only.
7. `UNKNOWN` remains unknown and blocks implicit mutation retry.
8. Every response identifies source, freshness, and unavailable fields.
9. Full content bodies are excluded from the compact semantic trace and normal
   projections. Under an admitted `FULL_EPISODE` policy, the protected learning
   store may preserve full secret-redacted model-visible prompts, messages,
   tool exchanges and artifacts as defined by
   `AETHER_LEARNING_EPISODE_SCHEMA.md`. Credentials, hidden chain-of-thought and
   unbounded provider/terminal debug payloads remain forbidden.
10. Protocol and provider versions are independent.
11. Opaque cursors are server-generated, integrity-protected, principal/project/
    Run-bound, and range-validated. Malformed, oversized, stale, or cross-scope
    cursors return `INVALID_CURSOR` without enumeration.
12. Replaying a completed `operation_id` returns the stable terminal
    result/effect receipt under a newly generated `request_id` and performs no
    provider work. Callers compare stable fields, not request IDs.

The operational surface contains exactly 15 designed tools:

```text
project_admit
project_inspect
swarm_validate
swarm_start
swarm_status
swarm_dispatch
swarm_message
swarm_reconcile
swarm_retry
swarm_cancel
swarm_close
swarm_trace
orca_search
orca_describe
orca_call
```

They remain unregistered and uncallable during the R0-R6 task.

## 2. Common types

### 2.1 Reason

```json
{
  "code": "PARALLEL_INDEPENDENT_SCOPE",
  "summary": "Backend and frontend scopes are independent after the API contract was frozen.",
  "authority_ref": "contract:onboarding/generation/3",
  "evidence_refs": ["git:abc123:docs/design/onboarding.md"]
}
```

`summary` is concise declared rationale, not chain-of-thought.

### 2.2 Effect class

```text
READ_ONLY
LOCAL_APPEND_ONLY
LOCAL_REVERSIBLE
LOCAL_DESTRUCTIVE
EXTERNAL_REVERSIBLE
EXTERNAL_IRREVERSIBLE
UNKNOWN
```

An operation whose actual effect cannot be classified is `UNKNOWN` and is denied
unless a separately approved diagnostic contract explicitly permits read-only
inspection.

`LOCAL_APPEND_ONLY` means a durable audit/contract/evidence append that can be
superseded by a later event but not erased or represented as mechanically
reversible.

### 2.3 Mutation identity

```json
{
  "operation_id": "01989f2f-8b67-7a42-8e1e-2c5d23ff6b50",
  "project_id": "01989f1d-54a7-7a9e-9dc4-8206cad0f6e3",
  "contract_id": "contract:onboarding/generation/3",
  "use_case_id": null,
  "reason": {"code": "...", "summary": "...", "authority_ref": "..."},
  "expected_effect": "LOCAL_REVERSIBLE"
}
```

The same `operation_id` plus the same canonical request is idempotent. Reuse with
different canonical input returns `IDEMPOTENCY_CONFLICT`.

### 2.4 Source-labelled field

```json
{
  "value": "running",
  "source": "orca",
  "observed_at": "2026-08-06T20:10:33.120Z",
  "freshness": "fresh"
}
```

Valid freshness values: `fresh`, `stale`, `historical`, `unknown`.

### 2.5 Result envelope

```json
{
  "protocol": "aether.mcp/v1alpha2",
  "ok": true,
  "request_id": "server-generated-id",
  "operation_id": "caller-operation-id-or-null",
  "trace_event_ids": ["event-id"],
  "effect": "LOCAL_REVERSIBLE",
  "outcome": "SUCCEEDED",
  "result": {},
  "unknowns": [],
  "warnings": [],
  "error": null
}
```

`ok: true` means the MCP call completed according to its contract. It does not
mean a worker result or product outcome was accepted.

### 2.6 Error envelope

```json
{
  "protocol": "aether.mcp/v1alpha2",
  "ok": false,
  "request_id": "server-generated-id",
  "operation_id": "caller-operation-id-or-null",
  "trace_event_ids": ["event-id-if-safe"],
  "effect": "UNKNOWN",
  "outcome": "REJECTED",
  "result": null,
  "unknowns": [],
  "warnings": [],
  "error": {
    "code": "PARTICIPANT_FORBIDDEN",
    "message": "The requested participant is not admitted for this task.",
    "retryable": false,
    "reconciliation_required": false
  }
}
```

Error text never includes secrets, submitted private data, raw provider bodies,
tracebacks, or foreign project details.

## 3. High-level Aether tools

### 3.1 `project_admit`

**Effect:** `LOCAL_APPEND_ONLY`

Admits one exact local project for the current coordinator principal. Inputs:

- mutation identity without caller-supplied `project_id`;
- canonical project-root candidate;
- optional safe project alias;
- requested maximum capture policy and consent/authority reference;
- structured reason and authority reference.

The MCP resolves the canonical root, Git common repository, current worktree,
branch/commit evidence, exact Aether/Hermes home, and coordinator profile. The
server creates or safely reuses an immutable `project_id`; a caller cannot select
another project's ID. Admission does not move, edit, initialize, or clean the
project.

Returns `project_id`, safe alias, restricted/fresh source-labelled identity,
admission generation, and any mismatch/unknown fields. A moved root requires an
explicit rebind event rather than silent path replacement.

### 3.2 `project_inspect`

**Effect:** `READ_ONLY`

Freshly verifies an admitted project's root/repository/worktree/profile binding
and returns source-labelled identity, containment, drift, and unknowns. It is
required before a new contract validation or mutation after restart/path change.

### 3.3 `swarm_validate`

**Effect:** `READ_ONLY`

Validates and canonicalizes a `SwarmManifest`; creates no Orca state.

Required manifest fields:

```json
{
  "protocol": "aether.mcp/v1alpha2",
  "project_id": "uuid",
  "contract": {
    "contract_id": "string",
    "generation": 1,
    "objective": "string",
    "acceptance": ["observable criterion"],
    "non_goals": ["excluded outcome"],
    "authorized_effects": ["LOCAL_REVERSIBLE"],
    "stop_condition": "string"
  },
  "evaluation": {
    "enabled": false,
    "use_case_id": null,
    "variant": null,
    "measurement_contract": null
  },
  "learning": {
    "capture_policy": "DISABLED|STRUCTURED_ONLY|FULL_EPISODE",
    "purpose": ["dogfood", "evaluation", "learning_candidate"],
    "consent_authority_ref": "decision-or-policy-ref"
  },
  "tasks": [
    {
      "task_key": "string",
      "deliverable": "string",
      "archetype": "hefesto",
      "dependencies": [],
      "read_scope": ["path-or-contract-ref"],
      "write_scope": ["path-glob"],
      "evidence_requirements": ["string"],
      "attempt_budget": 1,
      "placement": "current|child_worktree|read_only"
    }
  ]
}
```

Returns:

- canonical manifest;
- `manifest_digest`;
- validation findings;
- dependency order and ready set;
- participant/scope/effect decisions;
- compiled provider effect plan;
- unresolved material decisions;
- compatibility requirements;
- no mutation receipt.

Validation failure never partially creates a Run.

### 3.4 `swarm_start`

**Effect:** normally `LOCAL_REVERSIBLE`; may be higher if the admitted provider
plan contains a higher-class effect.

Inputs:

- mutation identity;
- `manifest_digest` and immutable canonical manifest reference;
- admitted Orca provider binding;
- start policy: create Run/Tasks and optionally dispatch every initial ready Task.

Behavior:

1. revalidate manifest generation, participant policy, provider schema, and
   project/workspace binding;
2. record the privacy-filtered canonical manifest generation and digest as an
   immutable Aether contract snapshot;
3. initialize the admitted capture-policy generation and episode envelope
   before any provider/model effect when learning capture is enabled;
4. append operation request;
5. create or bind one Orca Run;
6. materialize all admitted Tasks and dependency edges;
7. submit all initial independent ready Dispatches before observing any one;
8. record one receipt per effect;
9. return after dispatch acceptance, not worker completion.

Returns `SUCCEEDED`, `PARTIAL`, `REJECTED`, `FAILED`, or `UNKNOWN`, with exact
created/reused/rejected/unknown resources. No implicit unverified rollback.

### 3.5 `swarm_status`

**Effect:** `READ_ONLY`

Inputs:

- `project_id`;
- Aether `run_id`;
- optional cursor;
- `wait_ms` default `0`, bounded maximum;
- detail level: `summary`, `tasks`, `questions`, `evidence`, `resources`, or
  `diagnostic`.

Returns:

- Aether semantic phase;
- fresh source-labelled Orca snapshot;
- changes after cursor;
- Task/Dispatch/worker status;
- ready work;
- material questions and blockers;
- evidence/acceptance gaps;
- cleanup/survivor state;
- new cursor and unknowns.

Ordinary status polling is measured but not appended as full semantic events
unless it observes a material state transition.

### 3.6 `swarm_dispatch`

**Effect:** `LOCAL_REVERSIBLE`

Dispatches one or an independent batch of ready Tasks after revalidating:

- contract generation;
- dependencies;
- archetype policy/availability;
- exact profile home and allowed environment;
- placement and one-writer scope;
- concurrency and attempt budget;
- provider schema and operation identity.

Returns per-Task acceptance, Dispatch identity, worker/terminal/worktree binding,
and unknown effects. A batch contains independent submissions only; no hidden
ordering or rollback is inferred.

### 3.7 `swarm_message`

**Effect:** `LOCAL_APPEND_ONLY` for the durable operational message. Any worker
action influenced by the message remains bounded by its existing Task contract
and authorized-effect plan.

Allowed kinds:

```text
progress
artifact_reference
dependency_handoff
technical_question
reply
review_request
finding
blocker
completion_reference
steering
```

Inputs include exact run/task/dispatch sender and admitted recipient, kind,
bounded message payload, safe trace summary, decision-required flag, blocking
effect, and mutation identity.

A message cannot grant scope, authority, participants, protected effects,
evidence waiver, release, or acceptance.

Orca owns the full operational message. Aether stores identity, kind, safe
summary/content digest, receipt, and decision/blocking metadata.

### 3.8 `swarm_reconcile`

**Effect:** `LOCAL_APPEND_ONLY` in `observe` mode because reconciliation
evidence/receipt is durable; otherwise the maximum explicit provider effect
required to fence, plus the inherent trace append.

Inputs:

- project/Run and exact target operation/Task/Dispatch;
- mode: `observe` or `fence`;
- a new reconciliation operation identity, reason, and authority;
- evidence sources permitted for reconciliation.

Behavior:

1. query fresh Orca state/events and applicable Git/filesystem/process receipts;
2. correlate by exact operation/Run/Task/Dispatch/resource identity;
3. append a terminal result only when evidence proves it;
4. otherwise preserve `UNKNOWN` and return the missing evidence;
5. in `fence` mode, apply only a described, authorized provider fencing
   operation and verify it before making retry eligible.

Every mutating operation records `reconcile_after_utc` and
`lease_deadline_utc` longer than its normal provider budget. Deadline expiry
changes the state to `RECONCILIATION_REQUIRED`; it never turns an unknown effect
into success, failure, or retry permission automatically.

### 3.9 `swarm_retry`

**Effect:** `LOCAL_REVERSIBLE`

Requires:

- prior Task and Dispatch;
- classified prior outcome;
- evidence of terminality or fencing;
- failure/correction summary;
- remaining attempt budget;
- new operation identity;
- optional new contract generation when an authorized amendment occurred.

Always creates a new Dispatch identity. A stale or uncertain prior writer blocks
retry until reconciled.

### 3.10 `swarm_cancel`

**Effect:** `LOCAL_REVERSIBLE` or `LOCAL_DESTRUCTIVE` according to provider
semantics.

Targets one admitted Dispatch, Task, or Run scope. Returns cancellation request,
provider acknowledgement, current outcome classification, and resources still
requiring reconciliation. Cancellation is not aggregate cleanup.

### 3.11 `swarm_close`

**Effect:** generally `LOCAL_DESTRUCTIVE` because temporary runtime resources may
be removed. The exact effect plan must be declared and authorized.

Behavior:

1. stop new dispatch admission;
2. reconcile every Task and Dispatch;
3. verify evidence and semantic disposition;
4. request provider cleanup;
5. inventory workers, terminals, setup processes, worktrees, branches, messages,
   questions, sockets, temporary state, and retained artifacts;
6. append closure and integrity receipt.

Only resources linked to the Run by creation/admission receipts are eligible for
cleanup mutation. Pre-existing similarly named resources are reported but not
removed.

Returns:

- `CLOSED` only with zero unknown resources or explicit authorized retention;
- `BLOCKED` when a known issue prevents closure;
- `UNKNOWN` when aggregate disposition cannot be proven.

### 3.12 `swarm_trace`

Typed actions:

```text
query
record_decision
record_evidence
```

`query` is `READ_ONLY`. The two record actions are `LOCAL_APPEND_ONLY`, require a
mutation identity, and do not mutate Orca.

Query modes:

```text
timeline
explain
operations
decisions
evidence
retries
resources
metrics
integrity
export
```

Filters are project-bound and may include contract/run/task/dispatch/operation,
event range, use case, variant, event type, actor, and outcome. Cross-project
queries require separately admitted authority and never enumerate inaccessible
projects.

`explain` is deterministic and returns recorded rationale/evidence. It never
fabricates missing reasons.

`export` returns a bounded redacted bundle plus digest in the tool response. It
does not write an arbitrary filesystem destination; persisting that bundle is a
separate explicitly authorized artifact operation.

`record_decision` appends one explicit semantic decision with kind, concise
decision/rationale, authority reference, affected identities, and prior
generation where applicable. A contract amendment creates a new generation and
never rewrites history.

`record_evidence` appends bounded evidence type/reference, source/producer,
optional artifact digest, normalized check identity, observed outcome, criteria,
unknowns, limitations, and optional verifier identity. It stores references and
receipts, not arbitrary artifact bodies or raw terminal output.

## 4. Dynamic Orca tools

These tools are available only to the primary Hermes coordinator for admitted
capabilities, diagnosis, and recovery. Normal product work should prefer the
high-level tools.

They cannot bypass principal/project binding, contract generation, participant
policy, effect authorization, idempotency, provider-version pinning, privacy, or
trace requirements. Operations that alter swarm topology require the same
invariants as their high-level counterparts.

### 4.1 `orca_search`

Searches the pinned or candidate version-matched Orca operation catalog by
intent/capability/effect. Read-only.

### 4.2 `orca_describe`

Returns exact command/API identifier, arguments schema, output schema, effect
class, capability requirements, provider version and schema authority. Output,
effect, timeout or recovery fields may come from a version-pinned Aether schema
bundle accepted under `M0_PROVIDER_SEAM_AMENDMENT.md` when Orca's public catalog
omits them. Provider-declared and Aether-qualified fields must remain distinctly
labeled. Read-only.

### 4.3 `orca_call`

Invokes one described operation with:

- `command_id`;
- structured `arguments`;
- mutation identity for any non-read operation;
- catalog/schema digest;
- qualified schema-bundle digest when applicable;
- expected effect and reason.

No shell command, interpolation, undocumented field, or private storage access is
accepted.

### 4.4 Internal batch and observation capabilities

Independent batching is an adapter optimization, not a public Hermes tool. Every
member remains a described version-pinned operation with its own result; `PARTIAL`
is preserved and no implicit rollback/retry is inferred.

Eventual observation is used internally by status, reconcile, and trace. Orca
1.4.167 has no public event stream, so any polling/journal projection is labelled
`AETHER_OWNED` and `DEGRADED`; it cannot claim provider ordering/completeness.

## 5. Deferred learning-boundary operations (not operational MCP tools)

The following conceptual operations are not registered or included in the
15-tool operational contract. They remain design input for a separate default-off
learning boundary and later M7 gate. Captured content is inert data and cannot
grant tool or prompt authority.

### 5.1 `learning_capture`

**Effect:** `LOCAL_APPEND_ONLY`

Actions: `inspect`, `set`, `reduce`, `pause`, `resume`, and `seal`.

- `set` establishes a capture-policy generation before provider/model effects;
- `reduce`/`pause` apply immediately and append an explicit capture gap;
- `resume` never backfills missing content;
- escalation to `FULL_EPISODE` requires exact project/owner authority;
- `seal` verifies completeness, content/integrity roots, gaps, and quarantine
  state, then makes the episode immutable.

Quota or encryption-boundary failure pauses rich capture fail-visibly. It never
silently claims a complete episode.

### 5.2 `learning_label`

**Effect:** `LOCAL_APPEND_ONLY`

Appends a versioned outcome, correction, preference, failure, quality,
eligibility, contamination, consent, or retraction label to a sealed or active
episode/turn. Inputs include label authority, exact targets, evidence, confidence
class where applicable, and superseded label references.

Worker self-report cannot grant training eligibility. User acceptance of a Run
does not automatically label every turn as a gold response.

### 5.3 `learning_dataset`

**Effect:** `READ_ONLY` for `inspect`; `LOCAL_REVERSIBLE` or
`LOCAL_APPEND_ONLY` for `build`, `validate`, `seal`, and `revoke` according to
the described artifact/manifest effect.

Builds one local candidate from sealed episodes using a frozen purpose,
selection, redaction, transform, deduplication, consent, label, split and
contamination contract. Train/development/test splits are isolated by project/
task/use-case lineage, not random turns. Evaluation-only episodes cannot enter
training.

### 5.4 `learning_export`

**Effect:** `LOCAL_REVERSIBLE`

Writes one sealed, redacted dataset bundle plus manifest/digest to an exact
authorized local destination. It requires a new operation ID, purpose, dataset
digest, authority and effect plan.

It cannot upload data, invoke a provider trainer, spend money, start fine-tuning,
change a model/route/prompt/profile/skill, promote a candidate, or activate a
runtime.

## 6. Future owner/admin retention operation (not an operational MCP tool)

### 6.1 `project_forget`

**Effect:** `LOCAL_DESTRUCTIVE`

This is a future owner/admin-only operation. The operational Hermes MCP does not
expose or register it.

Deletes the complete MCP-held partition and restricted identity binding for one
admitted project. It never removes or edits project files, Git refs/worktrees, or
Orca resources.

Inputs:

- mutation identity with exact `project_id`;
- exact safe-alias confirmation;
- mode: `normal` or `privacy_emergency`;
- concise reason and exact owner authority;
- optional required prior export digest.

Normal mode requires every known Run closed with zero unknown resources and
complete event/episode/label/dataset/export lineage reconciliation.
`privacy_emergency` may delete MCP data while a Run is open/unknown only with
exact owner authority; it returns operational disposition as unknown and cannot
claim cleanup.

Local datasets containing the project must be rebuilt/removed or revoked before
normal completion. External exports/derivatives remain explicit blockers or
unknowns until their boundary confirms disposition; no tool claims a trained
model was “untrained.”

After verified deletion, the global MCP store may retain only a non-enumerable
idempotency tombstone containing forget-operation ID, salted project-ID digest,
completion timestamp, and outcome. It retains no path, contract, reason body,
actor, artifact, or evidence identity. Re-admission creates a new project ID.

### 6.2 Retention behavior

- R1–R3 normalized semantic/operation/metric data has no silent time expiry and
  remains until owner-authorized project forget.
- Protected learning episodes/datasets have no silent expiry and remain until an
  authorized prune/revoke/forget operation reconciles lineage.
- Credentials, hidden chain-of-thought and unadmitted content are never stored.
- R4 bounded redacted diagnostic attachments are disabled by default and, when
  explicitly enabled, expire within seven days with deletion verification.
- Individual semantic events cannot be selectively edited/deleted in
  `v1alpha2`; complete project forget preserves an honest boundary.

## 8. Protocol evolution

- `v1alpha2` is allowed to change only through versioned documented revisions.
- Required-field or semantic changes update the protocol identifier.
- Unknown response fields must be tolerated; unknown request fields are rejected
  until explicitly admitted.
- Every Run pins one provider catalog/schema digest.
- Historical events retain their original schema version and migrate through
  explicit readers rather than in-place meaning changes.
- A future stable `v1` requires executed compatibility, migration, restart,
  recovery, privacy, and trace-integrity evidence.

## 9. MCP resources and unsupported protocol features

Read-only resource templates:

```text
aether://protocol/v1alpha2
aether://project/{project_id}/contract/{generation}
aether://project/{project_id}/run/{run_id}/summary
aether://project/{project_id}/run/{run_id}/timeline
aether://project/{project_id}/run/{run_id}/closeout
aether://project/{project_id}/use-case/{use_case_id}/{variant}
```

Every resource is principal/project-bound, redacted, source-labelled, and
non-enumerating. A missing/foreign resource returns the same safe class. Resource
content is a projection/reference and does not replace Orca operational
authority.

`v1alpha2` exposes no MCP prompts, requests no MCP sampling, and does not rely on
server-initiated progress/notification delivery for correctness. MCP roots may
help locate a candidate project but are never authoritative; `project_admit` and
`project_inspect` establish identity.
