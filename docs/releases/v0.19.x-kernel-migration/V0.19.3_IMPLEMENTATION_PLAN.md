# v0.19.3 Implementation Plan — Executable Closure and ACPManager-Owned Cleanup

**Status:** GATE B PASSED — DETERMINISTIC CANDIDATE FROZEN; GATE C LIVE BLOCKED

**Decision:** Chris selected the canonical sequence on 2026-07-27: v0.19.3 cleanup precedes v0.19.4 handoff.

**Baseline:** `c6366c1` documentation closeout; technical foundation through `b759609`.

## 1. Hypothesis

A kernel task with trusted v0.19.2 evidence can reach semantic `CLOSED` only through a durable close intent, ACPManager-owned cleanup, a verifier-owned cleanup receipt, and proof that no managed resource survives. Every uncertainty or failed postcondition produces a non-closed state, including explicit `CLOSE_FAILED` where failure is known.

## 2. Authority chain

```text
trusted v0.19.2 evidence receipt
  -> KernelRunService validates semantic closure and current authority
  -> durable close.requested intent
  -> kernel cleanup coordinator
  -> OlympusRuntimeAdapter public lifecycle seam
  -> ACPManager owns cancel/close/process/session cleanup
  -> verifier-owned durable cleanup receipt
  -> kernel verifies zero survivors and releases remaining authority
  -> task.closed / CLOSED
```

Permanent boundaries:

- KernelRunService owns semantic closure and durable task state.
- ACPManager remains the sole process/session lifecycle owner.
- Harmonia remains default-off and does not decide closure.
- No direct ACP access outside ACPManager.
- No `PilotStore` write or legacy fallback from a kernel run.
- `CLOSED` is impossible without trusted evidence and verified cleanup.

## 3. State and event model

The exact public vocabulary will be frozen by RED tests before production edits, with these semantic phases:

```text
RUNNING
  -> CLEANUP_PENDING       via close.requested
  -> CLEANUP_IN_PROGRESS   via cleanup.requested
  -> CLEANUP_VERIFIED      via cleanup.receipt.recorded with survivors=[]
  -> CLOSED                via task.closed

Known failed cleanup       -> CLOSE_FAILED
Uncertain cleanup effect   -> RECONCILIATION_REQUIRED, never CLOSED
```

Semantic task failure, technical ACP terminality, cleanup failure, and cleanup uncertainty remain distinct.

Every close/cleanup artifact is bound to installation, project, run, task, attempt, contract generation, revocation epoch, dispatch message, logical session, ACP session, authority fence, evidence receipt and stable command identity.

## 4. Atomic implementation increments

### Increment 1 — Durable close intent

Add a kernel-owned `request_close()` command that:

- validates the existing semantic closure contract;
- requires the exact durable trusted evidence receipt;
- validates current run/task/attempt/session/contract/fence authority;
- persists exactly one typed `close.requested` event;
- projects `CLEANUP_PENDING`, never `CLOSED`;
- is payload-aware and idempotent;
- performs zero ACP, Harmonia or PilotStore effects.

Primary scope:

- `src/olympus_v3/coordination/workflow.py`
- `src/olympus_v3/coordination/kernel_runtime.py`
- `src/olympus_v3/coordination/projections.py` only if the typed reducer requires it
- new `tests/coordination/test_kernel_closure_intent.py`

Commit boundary: authenticated event schema, state algebra, replay and command only.

### Increment 2 — ACPManager-owned cleanup effect

Add a bounded cleanup coordinator that consumes one pending intent and calls only:

```text
OlympusRuntimeAdapter.cleanup_kernel()
  -> ACPManager.cleanup_persisted()/close()
```

It must persist intent before the external effect, use one stable cleanup command, survive repeated cancellation, distinguish completed/failed/unknown/reconciliation-required, and never interpret `Unknown session` as successful absence without an identity-bound resource proof.

Primary scope:

- `src/olympus_v3/coordination/kernel_dispatcher.py` or a narrowly named cleanup module
- `src/olympus_v3/coordination/olympus_adapter.py`
- `src/olympus_v3/acp_manager.py`
- focused cleanup executor and ACP lifecycle tests

### Increment 3 — Cleanup receipt and final closure

Add a typed verifier-owned cleanup receipt and final reducer. `task.closed` is accepted only when:

- trusted result evidence is present;
- close intent is authoritative;
- cleanup receipt identity matches exactly;
- all managed session, prompt-task, mapping, lease and process/transport postconditions are verified absent;
- no cleanup result is unknown;
- no stale authority or conflicting terminal event exists.

Known postcondition failure yields `CLOSE_FAILED`; uncertain effect remains `RECONCILIATION_REQUIRED`. Neither is `CLOSED`.

### Increment 4 — Restart/concurrency reconciliation

Prove restart reconstruction and one-owner cleanup across independent SQLite connections:

- restart after close intent before effect;
- restart after cleanup effect before receipt persistence;
- identical replay convergence;
- competing cleanup command rejection;
- stale-worker fencing;
- unknown-session reconciliation from durable identity-bound state;
- no managed survivor under `CLOSED`.

This increment may be merged with Increment 3 only if its RED matrix is written first and the combined change remains independently auditable.

## 5. First atomic RED contract

Command:

```python
KernelRunService.request_close(
    run_id,
    task_id,
    *,
    attempt,
    closure_input,
    command_id,
)
```

Expected event aggregate:

```text
task:{run_id}:{task_id}
```

Expected durable payload contains at least:

- `run_id`, `task_id`, `attempt`, `contract_id`;
- `contract_generation`, `revocation_epoch`;
- dispatch `message_id` and current fence;
- `logical_session`, `acp_session_id`;
- `evidence_receipt_id`;
- `closure_proposal_hash`;
- stable `cleanup_command_id` and caller `command_id`.

### Positive RED

With a valid current attempt, durable terminal observation, matching trusted receipt, exact authority and valid semantic closure input:

1. append exactly one `close.requested`;
2. project `CLEANUP_PENDING`;
3. persist exact receipt/proposal bindings;
4. expose one pending cleanup obligation;
5. make zero ACPManager, adapter, Harmonia and PilotStore calls;
6. never project `CLOSED`.

### Negative RED

Every rejection leaves ledger and projection unchanged:

- missing, stale, forged or conflicting evidence;
- unknown/cross-project run, task or session;
- stale, orphaned or superseded attempt;
- expired/replaced fence;
- revoked contract authority;
- technical terminal status incompatible with semantic proposal;
- direct `complete_task()` bypass;
- conflicting reuse of command or cleanup identity.

### Replay and fault RED

- identical command/payload is one event and one obligation;
- same command with different payload is an idempotency conflict;
- rebuild after commit reconstructs `CLEANUP_PENDING`;
- rollback before commit leaves no intent;
- crash after commit but before in-memory replay remains recoverable;
- malformed or contradictory history fails closed;
- contract/fence change between validation and append rejects atomically.

### Concurrency RED

Using two independent SQLite connections and barriers:

- same close command converges to one event;
- different close commands race to one winner;
- stale worker cannot append after authority replacement;
- restart replay racing a fresh caller cannot create a second obligation.

## 6. Gate B

Gate B requires:

- each production behavior preceded by an observed behavioral RED;
- focused closure/cleanup tests;
- complete coordination suite;
- full repository suite;
- Ruff check and format verification;
- `compileall`;
- `git diff --check`;
- exact changed-path and forbidden-dependency checks;
- secret scan over the complete patch candidate;
- explicit proof that config remains default-off;
- atomic commits restricted to v0.19.3 scope.

Blocking conditions:

- `CLOSED` without a zero-survivor cleanup receipt;
- generic unvalidated cleanup payloads;
- stale/cross-project authority accepted;
- unknown session interpreted as successful cleanup by absence of an in-memory row alone;
- duplicate cleanup effects or obligations;
- Harmonia direct ACP/lifecycle ownership;
- PilotStore write or legacy fallback;
- live ACP execution during Gate B.

## 7. Gate C — separately blocked

Gate B does not authorize a real Daimon, gateway restart or live ACP cleanup. Gate C requires a separate explicit user authorization after the deterministic candidate is frozen.

The future disposable live matrix must prove exactly one kernel authority, trusted evidence receipt, close intent, ACPManager-owned cleanup, cleanup receipt, zero survivors and final `CLOSED`, with rollback and a bounded cleanup deadline.

Any timeout, unknown session without durable reconciliation, surviving process/listener/mapping/lease, stale fence or missing receipt blocks Gate C and leaves the task non-closed.

## 8. Explicit deferrals

Not part of v0.19.3:

- v0.19.4 two-agent handoff;
- digest-bound result transfer to another Daimon;
- dynamic or bounded Harmonia next-task selection;
- arbitrary DAG or repair loops;
- Athena;
- broad pilot or production activation;
- merge, tag, release, publication or deployment.

## 9. Stop conditions

Stop the patch immediately on dual authority, direct ACP access outside ACPManager, semantic completion derived from technical status alone, cleanup retry after an uncertain effect without reconciliation, stale evidence/fence acceptance, `CLOSED` with any survivor, cross-project contamination, unbounded cleanup, or scope expansion into v0.19.4+.
