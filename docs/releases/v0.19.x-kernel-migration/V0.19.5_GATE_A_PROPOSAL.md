## 1. Hypothesis

Harmonia, remaining a deterministic coordination service rather than a Daimon or LLM agent, can select exactly one next eligible task from a kernel-issued bounded candidate projection without selecting a worker, amending the contract, calling ACP or becoming a second runtime authority.

Success requires this authority chain:

```text
immutable approved contract and task-worker bindings
  -> kernel derives revision-bound eligibility projection
  -> Harmonia applies one canonical deterministic policy and proposes selected_task_id
  -> kernel revalidates the proposal against durable state
  -> kernel commits one selection under durable CAS
  -> kernel resolves the worker from the immutable contract binding
  -> existing KernelDispatcher/ACPManager path stages and executes the task
```

The proposal records deterministic policy output; only the kernel authorizes and commits it.

## 2. Source-grounded baseline

- `ExecutionContract.task_worker_bindings` is immutable, participant-bound, permission-checked and included in canonical contract serialization.
- `KernelDispatcher._resolve_worker()` already rejects unbound tasks and resolves the worker only from the contract when bindings exist.
- `KernelDispatcher.stage_successor()` currently assumes a fixed successor and validates source closure, evidence, cleanup, handoff and binding before dispatch.
- `ProjectRuntimeContext._stage_fixed_successors()` is the narrow v0.19.4 seam to replace or generalize; it must not become an arbitrary DAG scheduler.
- `HarmoniaService.discovered_workers` is an admission guard, not selection authority.
- The ledger already provides signed drafts, aggregate expected-version writes, message deduplication, generation/revocation binding and durable replay.
- The current `plan_id` does not represent a Harmonia selection epoch or an eligibility projection digest.
- The in-process project lock cannot be the authority boundary across processes or restarts; durable SQLite CAS must decide contention.

## 3. Alternatives

### Option A — Harmonia selects only the task **(recommended)**

The immutable contract contains a bounded task set and one fixed worker binding per task. The kernel supplies eligible task IDs. Harmonia returns only `selected_task_id`; the kernel resolves the worker.

Advantages:

- smallest authority delta from v0.19.4;
- preserves one worker-authority seam;
- prevents worker injection and dynamic roster authority;
- supports compact deterministic CAS and replay tests.

Cost: worker substitution remains outside v0.19.5 and requires a later explicit design.

### Option B — Harmonia selects a task-worker pair

The contract would contain a pre-authorized matrix and Harmonia would select both values.

Rejected for this patch because it creates a second worker-selection authority, weakens `task_worker_bindings`, expands replay identity and tends toward dynamic capability/roster selection.

### Option C — Harmonia selects an opaque candidate token

The kernel would hash each task, binding and evidence tuple into an opaque token.

Technically safe but unnecessary for the smallest experiment. It reduces transparency and adds machinery without a current requirement to hide task topology from Harmonia.

## 4. Recommended authority contract

### 4.1 Immutable candidate set

The approved execution contract contains the complete bounded task set and exactly one worker binding per candidate task. Harmonia cannot create tasks, add workers, replace bindings or amend the contract.

For v0.19.5 the deterministic fixture is deliberately narrow:

- one already closed source task;
- two pre-authorized successor candidates;
- each candidate has the same exact trusted prerequisite source but a distinct fixed worker binding;
- at most one candidate may be selected for one selection epoch;
- no fan-in, arbitrary DAG, correction or retry loop.

### 4.2 Selection authority tuple

Every projection and proposal binds:

```text
installation_id
project_id
run_id
contract_id
contract_generation
revocation_epoch
selection_epoch
plan_revision
snapshot_digest
eligibility_projection_digest
```

`selection_epoch` is a durable monotonically increasing decision slot, not a wall-clock or in-memory value. The uniqueness authority is `(run_id, selection_epoch)`.

### 4.3 Kernel eligibility projection

Only the kernel derives the projection from the active immutable contract and trusted ledger state. Candidate order is canonical by `task_id`.

Each candidate contains audit metadata:

```text
task_id
resolved_worker_id
binding_digest
trusted prerequisite task/receipt identities
current task state
```

The resolved worker is visible for auditability but Harmonia cannot submit or alter it. A task is eligible only if:

1. it exists in the approved contract candidate set;
2. it has exactly one active immutable worker binding;
3. it is durably released by trusted evidence;
4. every source task is `CLOSED` with verifier-owned zero-survivor cleanup evidence;
5. its current state is `PROPOSED`;
6. active contract generation, revocation epoch, plan revision and snapshot digest match;
7. admission/concurrency limits permit selection.

Dynamic worker discovery, ACP state and agent prose never create eligibility.

An empty projection is valid and produces escalation, not fallback.

### 4.4 Deterministic Harmonia proposal

Harmonia applies the canonical policy `lowest canonical eligible task_id` to the exact kernel projection and returns a strict deterministic proposal containing:

```text
proposal_version
proposal_id
run_id
selection_epoch
contract_id
contract_generation
revocation_epoch
plan_revision
snapshot_digest
eligibility_projection_digest
selected_task_id
policy_id
policy_version
```

Forbidden fields include:

- worker or worker override;
- contract body or amendment;
- new evidence or prerequisite receipts;
- ACP session identity;
- retry/correction instruction;
- task graph;
- dispatch or lifecycle command.

The proposal has no independent signing credential because Harmonia is not a separate agent or trust principal in v0.19.5. Its canonical bytes and digest make the policy output replayable and auditable, while the kernel writer remains the only commit authority. Introducing an LLM selector, separate Harmonia identity or proposal key is deferred to a later explicit design.

### 4.5 Kernel validation and commit

The kernel re-derives current eligibility and validates every authority field, canonical policy identity/version, proposal digest, projection digest, selected membership, immutable worker binding, prerequisite receipt, closure/cleanup state, contract limits and aggregate version. It independently recomputes the policy result and rejects any different `selected_task_id`.

It commits exactly one kernel-authenticated `task.selection.committed` authority event for `(run_id, selection_epoch)`. The event binds:

```text
proposal_id and proposal_digest
eligibility_projection_digest
selected_task_id
kernel-resolved worker_id and binding_digest
source task and trusted close/cleanup identities
contract generation and revocation epoch
plan revision and snapshot digest
aggregate CAS version
```

The dispatch envelope is derived from the committed selection, never directly from the Harmonia proposal.

Lifecycle remains kernel-owned:

```text
PROPOSED -> ADMITTED -> READY -> DISPATCHED -> RUNNING
```

ACP effects remain exclusively:

```text
KernelDispatcher -> OlympusRuntimeAdapter -> ACPManager
```

### 4.6 Replay, contention and crash recovery

- Identical `proposal_id` and digest returns the original committed result with no second selection or dispatch.
- Reusing a proposal ID with different bytes is `idempotency_conflict`.
- A different proposal for an already committed selection epoch cannot win or select another task.
- Two concurrent proposals use durable SQLite CAS; exactly one commits.
- A losing proposal never silently selects its second choice.
- A crash before commit grants no selection authority.
- A crash after selection commit but before dispatch staging is recovered from the durable event and stages exactly once without consulting Harmonia again.
- Stale generation, epoch, projection, plan, snapshot, receipt or aggregate version fails closed without state mutation or ACP effect.
- External uncertainty after commit remains kernel-owned reconciliation; no Harmonia retry, Hermes relay or legacy fallback occurs.

### 4.7 Escalation

Escalate without automatic retry or fallback when:

- the candidate projection is empty or ambiguous;
- no candidate retains trusted eligibility;
- the deterministic policy is unavailable, unknown or produces a non-canonical result;
- contention cannot be resolved as an idempotent replay;
- prior selection commitment is uncertain;
- dispatch becomes externally uncertain after commit.

Escalation is a durable projection/event for Hermes and the user. It is not a task selection or contract amendment.

## 5. Deterministic Gate B increments

### Increment 1 — Projection and proposal authority

RED first:

- canonical projection ordering/digest;
- exact proposal parser, canonical policy identity and deterministic recomputation;
- reject worker injection, task/contract amendment and unknown candidates;
- reject stale generation, revocation, plan, snapshot and projection identities;
- proposal values cannot commit kernel events or override the kernel writer.

GREEN:

- immutable projection/proposal types;
- deterministic policy boundary with no model or agent call;
- no lifecycle or ACP effect.

### Increment 2 — Durable selection CAS

RED first:

- one `(run_id, selection_epoch)` winner across two SQLite connections;
- identical replay is idempotent;
- changed replay conflicts;
- two candidates racing produce one committed selection;
- losing proposal does not choose another candidate;
- stale proposal causes zero lifecycle mutation.

GREEN:

- kernel-authenticated `task.selection.committed` event;
- shared append/replay validation and projection;
- durable uniqueness and expected-version handling.

### Increment 3 — Committed-selection dispatch

RED first:

- dispatch derives only from committed selection;
- kernel resolves worker from immutable contract binding;
- crash after commit/before staging recovers exactly once;
- concurrent restart reconciliation produces one dispatch/attempt;
- no proposal can call ACP or bypass `KernelDispatcher`;
- external uncertainty never triggers fallback or second selection.

GREEN:

- narrow replacement/generalization of `_stage_fixed_successors()`;
- committed-selection reconciliation into existing dispatcher;
- no live configuration or activation.

### Increment 4 — Default-off public composition

RED first:

- disabled/absent mode creates no projection, runtime, ledger mutation or ACP call;
- existing one-task and fixed-two-task requests remain compatible;
- exact bounded candidate request only;
- status exposes sanitized projection/selection identities but no key, lease token or result body;
- ordinary `talk_to` remains unchanged.

GREEN:

- additive default-off public schema and projection;
- no Gate C live run.

## 6. Gate B acceptance matrix

The complete matrix must prove:

1. default-off zero effects;
2. legacy and v0.19.4 fixed-path compatibility;
3. immutable task-only candidate authority;
4. worker injection and task-worker pair forgery rejection;

14. contract binding is the only worker resolution source;

16. ACP uncertainty remains reconciliation-required;

## 7. Gate C remains separate

Gate A approval authorizes only deterministic Gate B implementation. It does not authorize:

- live Harmonia selection;
- live ACP or Daimon execution;
- configuration mutation or gateway restart;
- marking PR #113 ready or merging it;
- tag, release, publication, deployment or production migration;
- v0.19.6 fault pilot;
- alteration of preserved R8 work.

A later Gate C must freeze the disposable root, exact three-task candidate fixture, selection policy, proposal key, workers, prompts, budgets, fault boundary, expected ledger path, cleanup deadline and rollback trigger.

## 8. Strict non-goals

- dynamic roster/capability discovery as authority;
- Harmonia worker selection or substitution;
- task-worker matrices;
- mutable bindings or contract amendment;
- arbitrary DAG/fan-in/fan-out scheduling;
- arbitrary task creation;
- retry, repair, correction or re-proposal policy;
- direct Harmonia ACP calls;
- Harmonia evidence acceptance, lifecycle, cleanup, semantic completion or closure;
- Hermes routine result relay or next-agent selection after admission;
- legacy fallback after kernel admission;
- Etalides dependency;
- production activation or migration claim.

## 9. Stop conditions

Stop immediately on:

- two authorities for one selection epoch;
- any worker value accepted from Harmonia;
- candidate eligibility derived from discovery or prose;
- proposal directly causing ACP effect before kernel commit;
- stale proposal accepted;
- duplicate selection, attempt or ACP session;
- automatic second-choice selection after contention;
- hidden retry or legacy fallback;
- `PilotStore` write;
- cross-project contamination;
- scope expansion into v0.19.6.

## 10. Gate A decision

The package decision is closed:

### Option A — Approved recommended bounded model

Chris approved all of the following as one v0.19.5 authority contract:

1. Harmonia selects only `selected_task_id`; the kernel resolves the pre-bound worker.
2. The projection exposes the resolved worker only for auditability.
3. One durable selection epoch permits one winner and no implicit re-proposal.
4. Harmonia uses the canonical deterministic `lowest canonical eligible task_id` policy; no LLM, Daimon or separate Harmonia credential is introduced.
5. Empty, stale, ambiguous or contended selection escalates without automatic retry or legacy fallback.
6. Authorization covers deterministic Gate B and one isolated disposable demonstration after GREEN.

### Option B — Redesign worker selection

Permit Harmonia to select a task-worker pair from a pre-authorized matrix. This expands authority and requires redesign before implementation.

### Option C — Keep v0.19.5 parked

Preserve v0.19.4 as the last validated boundary and do not implement dynamic selection.

**Decision:** Chris approved Option A on 2026-07-27 and explicitly requested implementation plus an observable isolated demonstration. Global activation, production migration, PR merge, tag, release, deployment and preserved R8 mutation remain unauthorized.
