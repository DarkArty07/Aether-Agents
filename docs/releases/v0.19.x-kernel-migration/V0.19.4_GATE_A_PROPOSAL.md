# v0.19.4 Gate A Proposal — Fixed Two-Agent Digest-Bound Handoff

**Status:** GATE A APPROVED — DETERMINISTIC GATE B AUTHORIZED; GATE C LIVE BLOCKED

**Date:** 2026-07-27

**Baseline:** `7e432f5` (`v0.19.3` deterministic Gate B)

**Live state:** Gate C remains blocked; Harmonia remains default-off

## 1. Hypothesis

A fixed Task B can start from Task A's verifier-owned, ledger-bound result without Hermes relaying that result or selecting the next agent, while the kernel remains the sole workflow authority and ACPManager remains the sole process/session lifecycle owner.

Success requires one deterministic two-task trace:

```text
one initial fixed contract submission
  -> Task A bound to worker A
  -> trusted A evidence receipt
  -> immutable handoff snapshot
  -> durable release of Task B
  -> verified cleanup and CLOSED for A
  -> Task B bound to worker B
  -> digest-verified B input
```

There are zero routine Hermes calls between A and B.

## 2. Source-grounded constraints

- `RunRecord` owns one `contract_id`; current workflow replay is run-contract scoped.
- `TaskRecord` owns prerequisites and state, but no authoritative worker assignment.
- `KernelDispatcher.stage_ready()` currently derives one worker from the complete contract and therefore supports only a one-worker contract.
- `EvidenceReceipt` binds the source artifact's path, generation and SHA-256 digest without placing result content in the ledger.
- Evidence receipt plus `task.released` is already one SQLite transaction.
- `task.released` moves B only from `BLOCKED` to `PROPOSED`; it does not admit or dispatch it.
- v0.19.3 makes `CLOSED` conditional on ACPManager-owned cleanup and a verifier-owned zero-survivor receipt.
- v0.19.5, not this patch, owns dynamic Harmonia next-task selection.

## 3. Recommended authority model

Use **one immutable execution contract** for the run, containing exactly two fixed task-worker bindings:

```text
task-a -> complete Principal(worker-a)
task-b -> complete Principal(worker-b)
```

The contract, not `TaskRecord`, artifact content, Hermes, Harmonia or a worker response, is authoritative for assignment. A binding is usable only when:

1. the task belongs to the run;
2. the run names the same active contract;
3. contract generation and revocation epoch match;
4. exactly one binding exists for the task;
5. the complete bound Principal is a contract participant;
6. its permissions authorize the task;
7. the dispatch payload names the same worker.

Separate contracts for A and B are rejected for this patch because the current model is run-contract scoped. They would require a new cross-contract parent authority, two lifecycle histories and ambiguous generation/revocation ownership.

Task-local worker assignment without contract binding is also rejected because task creation would become a second authorization seam.

## 4. Immutable handoff input

B must not read A's ordinary mutable result path directly. A path plus a prior digest does not prevent replacement between receipt creation and B consumption.

After A's normal artifact verifies, the kernel creates a read-only, digest-addressed snapshot below the trusted project evidence root. Conceptual identity:

```text
.aether/evidence/<run>/handoffs/<source-task>/<receipt-id>/<sha256>.json
```

The snapshot contract contains only bounded metadata:

```text
source_run_id
source_task_id
source_attempt
source_receipt_id
source_artifact_generation
snapshot_relative_path
snapshot_digest
canonical_size_bytes
```

Requirements:

- source bytes are canonical verifier-accepted bytes;
- path is server-derived and contained below the trusted evidence root;
- copy uses exclusive creation and is immutable after publication;
- snapshot is re-read and hashed before its identity becomes durable;
- B re-verifies path containment, size and digest immediately before dispatch/consumption;
- result content is not duplicated into ledger events or Hermes messages.

A crash before ledger publication may leave an unreferenced file. It has no authority and may be garbage-collected only in a later patch.

## 5. Required ordering

### Initial fixed submission

1. One caller submits the complete fixed A/B contract and both bindings.
2. Kernel validates exactly two tasks: A has no prerequisite; B has exactly A.
3. Kernel persists the immutable contract, run and both tasks.
4. A starts `PROPOSED`; B starts `BLOCKED`.
5. Kernel admits, readies and stages A using A's contract binding.
6. Runtime dispatch remains `KernelDispatcher -> OlympusRuntimeAdapter -> ACPManager`.

### A evidence and release

7. Kernel records A's technical terminal observation.
8. Verifier validates A's result artifact against the complete authority tuple.
9. Kernel creates and verifies the immutable handoff snapshot.
10. In one SQLite transaction, kernel records:
    - A evidence receipt including snapshot identity; and
    - B `task.released` referencing the exact A receipt and snapshot.
11. B is `PROPOSED`, but is not yet admissible.

### Cleanup-before-handoff

12. Kernel records A close intent.
13. ACPManager performs bounded cleanup.
14. Kernel records cleanup outcome and verifier-owned receipt.
15. Kernel releases A's dispatch lease under its fence.
16. Only zero survivors permits `task.closed` for A.
17. Failed or unknown cleanup leaves B non-dispatchable.

### B admission and dispatch

18. Kernel verifies A is `CLOSED` and B's exact release/snapshot/contract binding still match.
19. Kernel re-verifies the snapshot.
20. Kernel advances B through `PROPOSED -> ADMITTED -> READY -> DISPATCHED`.
21. B receives the bounded handoff metadata and reads the snapshot under digest verification.
22. No routine Hermes call or next-agent selection occurs between A and B.

## 6. Approved public submission seam

### Option A — Extend `harmonia(action="start")` with an explicit fixed-two-task request **(recommended)**

The caller supplies both task specifications and both workers in the single initial request. Harmonia validates and composes the immutable contract but does not select B, inspect A's prose, relay results or call ACP directly. The kernel performs every transition after admission.

Advantages:

- preserves Harmonia as the public coordination identity established in v0.19.1;
- avoids a second public kernel tool;
- permits a real later Gate C through the supported surface;
- keeps dynamic selection absent and configuration default-off.

Cost: the public request schema grows by one explicit, bounded mode.

### Option B — Add an internal-only fixed-contract composition API

Useful for deterministic tests, but no supported public path could later prove zero-relay behavior without another design change. This risks validating a disconnected library rather than the product surface.

### Option C — Add a new public kernel/handoff tool

Rejected. It exposes implementation internals, duplicates Harmonia's public role and creates competing admission surfaces.

**Approved:** Option A. Chris approved this seam on 2026-07-27. `harmonia start` remains a caller-driven admission boundary; it does not become the planner. v0.19.5 later adds bounded selection as a separate authority delta.

## 7. Contract compatibility

Use an additive, explicit contract schema revision for task bindings. Legacy contracts remain readable and retain their existing one-worker interpretation. The fixed-two-task path requires the new schema and exact bindings; it must not infer missing bindings during replay.

Contract identity and canonical serialization include the binding map. Amendment, generation and revocation semantics remain unchanged. A binding change therefore cannot occur as mutable task data.

## 8. Deterministic Gate B increments

### Increment 1 — Contract-bound workers

RED first:

- exact A/B binding round-trip and replay;
- reject missing, duplicate, nonparticipant, wrong-project and actor-only ambiguous bindings;
- reject caller/dispatch worker overrides;
- legacy one-worker contract behavior unchanged.

GREEN:

- additive contract schema support;
- task-specific worker resolution in `KernelDispatcher`;
- no public/runtime activation.

### Increment 2 — Verifier-owned handoff snapshot

RED first:

- immutable snapshot from verified A artifact;
- source mutation after receipt cannot affect B;
- missing/replaced/out-of-root/wrong-size/digest-mismatched snapshot rejected;
- crash before ledger publication grants no handoff authority.

GREEN:

- snapshot identity and verifier;
- receipt/release payload binding;
- atomic SQLite persistence.

### Increment 3 — Cleanup-gated successor admission

RED first:

- B cannot be admitted after receipt/release while A is non-closed;
- failed/unknown A cleanup blocks B;
- restart before A closure does not dispatch B;
- restart after A closure stages exactly one B dispatch;
- stale generation, epoch, attempt, lease, receipt or binding rejects B.

GREEN:

- kernel-owned eligibility check;
- deterministic B advancement and dispatch envelope;
- no Hermes relay path.

### Increment 4 — Fixed public composition

Applies only if Option A is approved.

RED first:

- exact two-task request only;
- both bindings caller-fixed and contract-authorized;
- no dynamic selector or result relay;
- existing one-task request and default-off behavior unchanged;
- disabled configuration performs zero runtime calls.

GREEN:

- bounded `harmonia start` request variant;
- one initial admission creates A and B;
- no Gate C or live ACP.

## 10. Gate C remains separate

No live execution is authorized by approval or implementation of this proposal. A future Gate C must separately freeze:

- disposable project/control root;
- exact workers A and B;
- complete immutable contract and prompts;
- snapshot/evidence paths;
- time, attempt, effect and cleanup budgets;
- expected ledger location;
- zero-Hermes-relay trace metric;
- fault and rollback matrix.

## 11. Explicit non-goals

- dynamic next-task selection;
- arbitrary DAG, fan-in/fan-out or graph scheduling;
- repair/correction loops;
- worker selection from A's output;
- separate per-task contracts;
- per-task budget redesign;
- result bodies in ledger or Hermes messages;
- snapshot garbage collection;
- semantic acceptance derived from technical terminality;
- Harmonia ACP lifecycle ownership;
- Etalides dependency;
- Gate C live execution;
- activation, config mutation, gateway restart, merge, tag, release, publication or deployment.

## 12. Stop conditions

Stop immediately on dual authority, mutable or out-of-root handoff input, dispatch to an unbound worker, B dispatch before A `CLOSED`, result relay through Hermes, Harmonia choosing B, stale identity acceptance, duplicate external effect, cross-project contamination, unbounded retries/resources or scope expansion into v0.19.5.
