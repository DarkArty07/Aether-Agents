## 1. Authorization boundary

This plan authorizes no source change, configuration change, ACP execution, gateway restart, merge, tag, release, deployment or publication. It defines the implementation gate for a later explicit authorization.

v0.19.1 has one hypothesis:

> One explicitly authorized, single-task Harmonia request can traverse the real server-owned kernel composition into `ACPManager`, with durable admission, dispatch staging and ACP session binding, while `talk_to` remains legacy and no semantic completion is claimed.

The patch ends at technical composition evidence. It does not prove useful work, trusted evidence, closure, handoff, active Harmonia planning or replacement of Hermes.

```text
MCP request
  -> server._handle_harmonia()
  -> HarmoniaService
       -> ProjectStoreResolver
       -> ProjectInspector                 [status only, read-only]
       -> ProjectRuntimeRegistry           [start/stop, lazy]
            -> SQLiteLedger                [one project authority]

```

- action-specific input DTO validation;

- stable public response/error DTOs.

#### Create `src/olympus_v3/coordination/harmonia_store.py`

Owns:

#### Create `src/olympus_v3/coordination/harmonia_runtime.py`

Owns:

- `ProjectRuntimeContext`;

- lazy composition of ledger, writer, runtime, dispatcher and adapter;
- per-project admission locks;
- bounded, idempotent resource shutdown.

No TTL, eviction thread, plugin factory or second ACP manager is permitted.

#### Create `src/olympus_v3/coordination/harmonia_service.py`

Owns:

- effective admission evaluation;
- `start`, `status` and `stop` orchestration;
- exact replay/conflict handling;

It may call `KernelRunService`, `KernelDispatcher`, the registry and inspector. It must not call `ACPManager`, inspect `ACPManager.agents/sessions`, write `PilotStore`, or infer semantic completion.

- `coordination/__init__.py`: export only Harmonia domain types needed by server/tests; kernel implementation remains non-public MCP detail.
- `server.py`: register/route one `harmonia` tool and own init/shutdown.

## 4. Public MCP contract

The tool remains one flat action-typed MCP surface:

```text
harmonia(
    action="start" | "status" | "stop",
    project_root="/absolute/project/root",
    request_id="...",          # start only
    contract={...},             # start only
    plan_revision=1,            # start only
    snapshot_digest="sha256:...", # start only
    run_id="...",              # status/stop only
    reason="...",              # optional stop metadata
)
```

Unknown actions, unknown properties and action-incompatible properties fail closed. There is no nested arbitrary payload, no caller-selected `project_id`, ledger path, `run_id`, `task_id`, ACP session ID, writer ID, key ID or runtime authority.

### `start` request

Required fields:

- `action="start"`;
- `project_root`: existing absolute directory, canonicalized by the server;
- `request_id`: lowercase bounded identifier matching the existing kernel identifier grammar;
- `contract`: restricted immutable `HarmoniaGenesisSpec` below;
- `plan_revision`: positive integer;
- `snapshot_digest`: algorithm-prefixed lowercase digest; v0.19.1 accepts only `sha256:<64 hex>`.

`request_id` is an idempotency identity, not an authorization token.

### Restricted `HarmoniaGenesisSpec`

The public DTO contains only values the caller is allowed to propose:

```json
{
  "worker": "hefesto",
  "objective": "one explicit task objective",
  "expected_outcome": "one technical deliverable expectation",
  "included_scopes": ["path/or/scope"],
  "excluded_scopes": ["forbidden/path"],
  "worker_permissions": ["read", "write"],
  "time_seconds": 600,
  "model_budget": 100,
  "qa_reserve": 1,
  "recovery_reserve": 1,
  "escalation_conditions": ["ambiguity"]
}
```

The server derives and freezes:

- `project_id` from canonical root;
- `contract_id` from canonical contract digest;
- owner principal as Hermes for the derived project;
- exactly one worker principal under the same owner/project;
- `generation=0`;
- `revocation_epoch=0`;
- `status=ACTIVE`;
- `concurrency=1`;
- `retries=0`;
- empty evidence gates for this patch;
- `SideEffectPolicy(allowed_effects=(), max_external_actions=0, reversible=True)`;
- completion and amendment authority as the Hermes owner.

The worker must be a discovered Daimon profile. The start request cannot name Hermes, Harmonia, Athena or an unknown profile as the worker. Athena remains suspended.

There is no separate `TaskSpec`. For v0.19.1 the contract objective is the one task. A second task description would create two mutable sources of truth.

### Derived identities

Use domain-separated SHA-256 over UTF-8 canonical data:

```text
installation_id = sha256("olympus-installation-v1\0" + canonical_aether_home)
project_id      = sha256("olympus-project-v1\0" + canonical_project_root)
contract_id     = "contract-" + sha256(canonical_genesis_contract)[:32]
run_id          = "run-" + sha256(project_id + "\0" + request_id)[:32]
task_id         = "task-" + sha256(run_id + "\0primary")[:32]
request_digest  = sha256(canonical start fields excluding action)
```

Equivalent roots resolve to one project ID. Different roots, even with the same basename, resolve to different IDs. Symlink policy must match `ACPManager._canonical_project_root()`; do not implement a competing normalizer.

### `status` request

Required:

- `action="status"`;
- `project_root`;
- `run_id`.

It performs no ACP poll, runtime composition, migration, directory creation or write. The derived project identity must own the requested run.

### `stop` request

Required:

- `action="stop"`;
- `project_root`;
- `run_id`.

Optional:

- `reason`: bounded informational text, never a semantic outcome.

`stop` reconstructs the current durable dispatch authority, appends `cancel.intent`, then delegates cancellation through `KernelDispatcher → OlympusRuntimeAdapter → ACPManager.close`. It never directly closes a process/session.

### Stable response envelope

```json
{
  "action": "start",
  "ok": true,
  "runtime_authority": "kernel",
  "project_id": "...",
  "run_id": "...",
  "task_id": "...",
  "contract_id": "...",
  "state": "session_bound",
  "durable": true,
  "attempt": 1,
  "outbox_status": "LEASED",
  "acp_session_id": "...",
  "uncertainty": null,
  "error": null
}
```

`durable=true` means only that the represented state is backed by committed ledger data. It never means semantic completion or verified cleanup.

Stable success/technical states:

- `admitted`;
- `dispatch_staged`;
- `retry_wait`;
- `session_bound`;
- `reconciliation_required`;
- `cancel_requested`.

Stable error codes:

- `feature_disabled`;
- `invalid_request`;
- `project_not_allowed`;
- `key_provider_unavailable`;
- `storage_unavailable`;
- `schema_incompatible`;
- `contract_conflict`;
- `idempotency_conflict`;
- `admission_limit`;
- `not_found`;
- `authority_mismatch`;
- `external_unknown`;
- `internal_failure`.

Errors and logs must not expose SQLite statements, stack traces, raw prompts, secrets, keys, environment values or arbitrary filesystem internals.

## 5. Configuration and effective admission

Extend `CoordinationConfig` to represent:

```yaml
coordination:
  enabled: false
  mode: legacy
  allowed_modes:
    - legacy
  project_allowlist: []
  max_active_runs: 0
```

Compatibility rules:

- absent config and explicit `enabled: false` produce zero Harmonia composition and zero ACP effect;
- explicit legacy v0.19.0 `mode: shadow` remains parseable for frozen shadow tests but does not enable Harmonia;
- `talk_to` remains legacy regardless of these values;
- `mode` never acts as a global request rerouter;
- unknown keys and malformed types fail configuration loading;
- `project_allowlist` contains absolute project roots, canonicalized once at server initialization;
- `max_active_runs` accepts only `0` or `1` in v0.19.1 and is interpreted per project;
- `0` denies new starts;
- `1` permits one distinct durable run for that project; an exact replay does not consume another slot;
- no terminal state exists in v0.19.1, so the slot is not released by `stop`.

Effective start admission is:

```text
explicit start request
AND coordination.enabled is true
AND "kernel-single-task" is in allowed_modes
AND canonical project root is allowlisted
AND max_active_runs == 1
AND internal signing keys are available
AND exact genesis contract is valid/current
AND no different durable run exists for the project
```

Config loading and server startup never create a project directory, ledger, run or ACP session.

The implementation and live configs remain different gates. Gate B tests inject config and fake keys in memory. Gate C requires a separately approved temporary config.

## 6. Project store and key custody

### Store location

The request cannot select a database path. Derive it under the server's configured Aether state root:

```text
<canonical AETHER_HOME>/.olympus/projects/<project_id>/coordination-v0.19.1.sqlite
```

The `StoreScope` is `(installation_id, project_id)`. Scope, registry key, allowlist result, contract principals, dispatch authority and ACP project root must all derive from the same canonical root.

There is no global Olympus session DB authority and no `PilotStore` read/write/projection.

### Read-only status

`ProjectInspector` must:

1. derive the expected path internally;
2. check that parent and DB already exist;
3. open SQLite using a URI read-only mode and `PRAGMA query_only=ON`;
4. validate an allowlisted schema/version without invoking `_schema()` or migrations;
5. query only known contract/event/outbox tables;
6. close the connection in all paths;
7. return categorized missing/corrupt/incompatible results.

Tests fingerprint the directory before/after status. No DB, WAL, SHM, migration, chmod or parent directory may appear from an absent-store status call. For an active WAL database, tests must prove the inspector sees committed state without writing a side file; if the platform cannot satisfy both properties, implementation stops and the read path is redesigned before source wiring.

### Key custody

No key material appears in MCP input, config YAML, ledger payload, response or logs.

`CoordinationKeyProvider` supplies internally:

- writer ID and key ID;
- writer authentication key;
- integrity key and key ID.

Deterministic tests inject fixture keys. The environment-backed provider reads these dedicated variables from the existing server environment:

```text
AETHER_COORDINATION_WRITER_KEY_B64
AETHER_COORDINATION_INTEGRITY_KEY_B64
```

Both values must be strict base64 that decodes to at least 32 bytes. The v0.19.1 identities are fixed as:

```text
writer_id       = hermes
writer_key_id   = harmonia-writer-v1
integrity_key_id = harmonia-integrity-v1
writer_resource = harmonia-ledger-owner
```

Missing, malformed or undersized values fail closed before ledger creation. The provider never auto-generates ephemeral keys because restart must preserve verification capability. Operational provisioning must be documented without values before Gate C.

## 7. Durable start sequence

All steps before dispatch are synchronous/durable and occur under a per-project async admission lock. v0.19.1 explicitly supports one Olympus server process; multi-process concurrent admission is not claimed.

```text
1. Validate action DTO and reject unknown fields.
2. Canonicalize root and derive installation/project/store identity.
3. Evaluate config, allowlist, cap and key provider before creating storage.
4. Convert HarmoniaGenesisSpec into exact ExecutionContract.
5. Compute contract and request digests plus run/task IDs.
6. Lazily obtain one ProjectRuntimeContext from the registry.
7. Ensure genesis:
   - empty scope -> create the exact generation-zero ACTIVE contract;
   - exact existing genesis -> idempotent continuation;
   - different/inactive/revoked genesis -> contract_conflict.
8. Ensure run using ledger CAS:
   - append v0.19.1 run.created with request_id/request_digest;
   - exact existing event -> replay;
   - same request_id/run_id with different digest -> idempotency_conflict;
   - any different run in this project -> admission_limit.
9. Ensure exactly one deterministic task and advance only through:
   created -> admitted -> ready -> dispatched -> attempt 1 active.
10. Stage exactly one DispatchEnvelope before ACP.
11. Dispatch through OlympusRuntimeAdapter.
12. Return a projection of committed state.
```

Genesis and run creation are recoverable phases. A crash after exact genesis but before `run.created` performs no ACP effect; replay of the identical request resumes. A mismatching request cannot adopt or replace that genesis.

### Backward-compatible workflow schema

Keep the current `run.created` schema valid for frozen R11 stores. Add a v0.19.1 variant:

```json
{
  "run_id": "...",
  "contract_id": "...",
  "mode": "kernel",
  "request_id": "...",
  "request_digest": "sha256:..."
}
```

`KernelRunService.ensure_run()` uses aggregate version/CAS rather than check-then-write alone. Existing `create_run()` behavior and tests remain unchanged. Projection/rebuild must accept both variants and retain enough request metadata for exact replay inspection.

### Contract-derived Daimon prompt

The current dispatcher sends identifiers but no useful task objective. v0.19.1 must derive the ACP message from the ledger contract, never from a second free-form post-admission payload.

The canonical message contains:

- `kind="aether.harmonia.single_task"`;
- installation/project/run/task/attempt IDs;
- contract ID, generation and revocation epoch;
- contract digest;
- plan revision and snapshot digest;
- exact objective and expected outcome;
- included/excluded scopes;
- permissions for the selected worker;
- no-side-effect policy and limits;
- escalation conditions.

The dispatcher verifies the active contract immediately before staging and again before effect using existing generation/revocation/fence checks. Prompt serialization is deterministic and contains no secret material.

## 8. ACP acceptance and uncertainty

### Required distinction

- Failure before any ACP session is opened may be retryable if the adapter can prove non-acceptance.
- Once `spawn_agent()` returns an ACP identity, send failure is not classified as a clean pre-acceptance failure.
- Timeout or ambiguous send after session creation becomes durable `UNKNOWN`/reconciliation required.

Introduce an internal typed adapter error carrying the known logical/ACP identity without exposing transport internals. `KernelDispatcher` uses it to preserve binding/uncertainty evidence. Bounded cleanup is requested only through `ACPManager`; cleanup success does not become semantic completion or verified closure.

If persistence of `session.bound` fails after ACP acceptance, the existing conservative `UNKNOWN` behavior remains mandatory. The effect is never retried as if it were pre-acceptance.

### No automatic semantic observation

`start` may synchronously return after technical dispatch acceptance. `status` never polls ACP. Any future active observation loop, result verification or completion belongs to later patches.

## 9. `status` and `stop` state model

### Status precedence

The inspector reports the most conservative committed state:

1. outbox `UNKNOWN` or `reconciliation_required=1` -> `reconciliation_required`;
2. `cancel.intent` -> `cancel_requested` with `cleanup_unverified`;
3. durable `session.bound` -> `session_bound`;
4. retry wait/poison -> `retry_wait` or categorized blocked state;
5. durable dispatch stage -> `dispatch_staged`;
6. durable run/task admission only -> `admitted`;
7. no matching run -> `not_found`.

Technical ACP status, process liveness, semantic completion and cleanup success are never inferred from absence, prose, a manager cache or an outbox ACK.

### Stop sequence

```text
1. Validate and derive project/run identity.
2. Obtain the existing runtime context; never create a new run/contract.
3. Rebuild and verify exact current authority and fence.
4. Idempotently append cancel.intent before external cleanup.
5. Call KernelDispatcher.deliver_cancel_with().
6. Adapter delegates to ACPManager.close(session_id, terminal_status="cancelled").
7. Return cancel_requested plus the narrowest honest uncertainty.
```

Response rules:

- committed intent + known close return -> `cancel_requested`, `uncertainty="cleanup_unverified"`;
- committed intent + timeout/error -> `cancel_requested`, `uncertainty="cancel_delivery_unknown"`;
- missing/mismatched/stale authority -> fail closed with no ACP effect;
- repeated stop returns the existing durable intent and must not close a replacement session;
- never return `stopped`, `closed`, `completed`, `failed` or `cancelled` as semantic state.

Durable cleanup receipts and `CLOSE_FAILED` belong to v0.19.3.
