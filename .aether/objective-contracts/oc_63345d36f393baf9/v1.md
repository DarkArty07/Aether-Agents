# Objective Contract: Repair affinity flow liveness and record HLP-280

## Owner Intent

The owner explicitly approves implementing the #280 affinity-flow liveness correction in Aether's downstream Hermes runtime. Every framework byte changed, added or activated must be recorded in `HERMES_LOCAL_PATCHES.md` with exact scope, evidence, backup, patch identity, activation state and retirement gate. The owner accepts that Aether already maintains a transitional modified Hermes and requires this repair to remain bounded, reversible and inspectable.

## Objective

Close Aether issue #280 by repairing the HLP-211b state machine so an affinity terminal controller with pending `flow_attention` cannot remain parent-gated in `todo` after explicit external recovery, and so an affinity coordinator cannot persist a silent non-dependency block. Implement and qualify the minimal downstream Hermes change, preserve ordinary parent gating and silent internal recovery, publish an independent HLP-280 patch and complete ledger record, activate it reversibly, and prove the exact owner-facing liveness path without an external watcher.

## Decisions and Assumptions

Approved design decisions and assumptions:

1. Repair the state machine in downstream Hermes; do not compensate from an Aether plugin, cron, watcher or SQL script. Assumption: atomic Kanban lifecycle transitions belong in the Hermes kernel.
2. Reuse public `kanban_unblock`; do not add a new tool, CLI verb, table, service or notification kind.
3. Add one narrowly validated exception: a terminal-affinity controller with an unresolved `flow_attention` may transition `blocked` or already-stranded `todo` to `ready` after explicit unblock even while the referenced blocker parent remains open. Ordinary `todo`/blocked cards remain parent-gated.
4. Correct the idempotent attention path: rediscovering the same pending attention may requeue a `todo` controller without duplicating `flow_attention`; it must not auto-promote a deliberately `blocked` controller before explicit recovery.
5. Reject, before durable mutation, a non-`dependency` block by an affinity coordinator when `origin_signal` is absent. The worker must choose `input`, `revision` or `recovery`; signals are not inferred automatically. `dependency` remains silent and allowed.
6. Do not change gateway/TUI production routing. Affinity subscriptions remain limited to explicit `origin_signal` and `flow_terminal`; internal recovery milestones stay silent.
7. Implement against an isolated candidate reconstructed from the exact active Hermes bytes. The loaded editable checkout is a shared dirty runtime and must not be used as the development worktree.
8. Version the correction as an incremental `patches/hermes/HLP-280-affinity-controller-requeue.patch` depending on HLP-211/HLP-211b. Do not rewrite the historical HLP-211b patch.
9. The production change should remain below 100 added/changed lines and limited to `hermes_cli/kanban_db.py` plus only the minimal tool-contract adjustment in `tools/kanban_tools.py`. Exceeding this or requiring gateway/TUI production changes triggers stop/review.
10. Reconcile the patch index sufficiently to make it truthful: add HLP-280, add the omitted active HLP-247 row, update the reconciliation date/status headings affected by current evidence, and enumerate every HLP-280 file/hunk/hash/line count/test/backup/activation/retirement fact. Do not retire unrelated patches in this objective.
11. Upstream `NousResearch/hermes-agent@b6f42c667a59469b477220254fec6e2486e30e51` lacks affinity/flow primitives; no upstream PR is part of this repair. The existing PR #75951 covers only same-card resume.
12. Canonical project documentation remains English. Runtime evidence must be bounded to identifiers, hashes, counts, statuses and event kinds; no prompts, transcripts, logs or secrets.

## Stop Conditions

Stop and surface evidence before further mutation if:
- the deterministic RED does not reproduce on exact captured bytes;
- any active target hash changes before backup/application, another process owns a target write, or candidate provenance cannot be reconstructed exactly;
- the repair exceeds 100 production lines, requires gateway/TUI production changes, a new tool/status/table/service, or broad refactoring of `kanban_db.py`;
- ordinary parent gating, sticky blocks, affinity fencing, Project/flow isolation or notifier deduplication regress;
- upstream gains an equivalent verified implementation before integration;
- the patch cannot apply/reverse/reconstruct byte-for-byte, includes hunks from another HLP, or the ledger cannot attribute every framework byte;
- required tests/build/checks fail after bounded correction, or a skip covers the exact acceptance path;
- activation requires new credentials/providers/spend, unrelated service mutation, or changing a project principle/authority boundary;
- gateway reload is unhealthy, target readback differs, two writers can claim the controller, origin wakes more than once, repairable work wakes the owner, or the live flow has no executable frontier without signal/terminal event.

Activation failure enters bounded Aether/Hermes recovery: restore the exact backup, reload once, run the last-known-good canary, and stop when green. At most two focused repair variants are allowed; do not add hardening, framework redesign or unrelated cleanup. A genuine protected-edge denial stops the objective.
