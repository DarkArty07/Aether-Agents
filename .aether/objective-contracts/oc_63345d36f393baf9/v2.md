# Objective Contract: Repair affinity flow liveness and record HLP-280

## Owner Intent

The owner explicitly approves implementing the #280 affinity-flow liveness correction in Aether's downstream Hermes runtime and, after the live v1 execution exposed a second same-class stall, also approves controller-first routing for automatic non-affinity child terminal failures (`protocol_violation`, `gave_up`, and equivalent circuit-breaker outcomes). The production cap is raised from 100 to 130 changed lines. Every framework byte changed, added or activated must be recorded in `HERMES_LOCAL_PATCHES.md` with exact scope, evidence, backup, patch identity, activation state and retirement gate. The v1 candidate and its verified evidence are reusable antecedents but v1 must not be activated.

## Objective

Close Aether issue #280 by completing the HLP-211b liveness state machine across both explicit and automatic blocker paths: (a) an affinity terminal controller with pending `flow_attention` cannot remain parent-gated in `todo` after explicit external recovery; (b) an affinity coordinator cannot persist a silent non-dependency block; and (c) an automatic terminal failure of a non-affinity child inside an affinity flow cannot leave the terminal controller parent-gated without `flow_attention`, `origin_signal`, or `flow_terminal`. Implement and qualify the minimal downstream Hermes change, preserve ordinary parent gating and silent internal recovery, publish an independent HLP-280 patch and complete ledger record, activate it reversibly, and prove the exact owner-facing liveness path without relying on an external watcher.

## Decisions and Assumptions

Approved design decisions and assumptions:

1. Repair the state machine in downstream Hermes; do not compensate from an Aether plugin, cron, watcher or SQL script. Atomic Kanban lifecycle transitions belong in the Hermes kernel.
2. Reuse public `kanban_unblock`; add no new tool, CLI verb, table, status, service or notification kind.
3. A terminal-affinity controller with unresolved `flow_attention` may transition `blocked` or already-stranded `todo` to `ready` after explicit unblock even while the referenced blocker parent remains open. Ordinary cards remain parent-gated.
4. Rediscovering the same pending attention may requeue a `todo` controller without duplicating `flow_attention`; it must not auto-promote a deliberately `blocked` controller before explicit recovery.
5. Reject before durable mutation a non-`dependency` block by an affinity coordinator when `origin_signal` is absent. Require `input`, `revision` or `recovery`; infer no signal. Silent `dependency` remains allowed.
6. Extend controller-first routing to automatic terminal failures of non-affinity children in an affinity flow, including `protocol_violation`/`gave_up` and same-class circuit-breaker outcomes produced by spawn/crash/timeout paths. When exactly one valid direct terminal-affinity controller exists, enqueue/requeue one `flow_attention`; if the failing card itself is terminal-affinity, retain `flow_terminal`. Ambiguous/no-controller graphs fail closed to existing behavior and must not adopt across Project/flow.
7. Automatic failure routing must not wake the owner for repairable internal work. The terminal controller attempts recovery first and only explicit `origin_signal` or `flow_terminal` crosses to origin.
8. Do not change gateway/TUI production routing. Affinity subscriptions remain limited to explicit `origin_signal` and `flow_terminal`.
9. Implement against an isolated candidate reconstructed from exact active Hermes bytes. The loaded editable checkout is shared dirty runtime and is not a development worktree.
10. Version the complete correction as incremental `patches/hermes/HLP-280-affinity-controller-requeue.patch` depending on HLP-211/HLP-211b. The v1 patch/commit `655b0cb0349e26cfaaf196849680ed83bed56067` and its RED/GREEN evidence are antecedents to extend, not artifacts to activate unchanged. Do not rewrite historical HLP-211b bytes.
11. The complete HLP-280 production change must remain at or below 130 additions+deletions and be limited to `hermes_cli/kanban_db.py` plus the minimal tool-contract adjustment in `tools/kanban_tools.py`. Exceeding this or requiring gateway/TUI production changes triggers stop/review.
12. Reconcile the patch index sufficiently to make it truthful: add HLP-280, add the omitted HLP-247 row, update affected dates/status headings and hotspots, and enumerate every HLP-280 file/hunk/hash/line count/test/backup/activation/retirement fact. Do not retire unrelated patches.
13. Upstream lacks affinity/flow primitives; no upstream PR is part of this repair. Canonical documentation remains English and runtime evidence remains bounded to identifiers, hashes, counts, statuses and event kinds.

## Acceptance Criteria

- Pre-change candidates reproduce both defects deterministically: (A) explicit controller unblock lands `todo`, controller unclaimable with pending attention; (B) a non-affinity child automatic terminal failure (`protocol_violation`/`gave_up`, plus representative same-class failure path) produces no controller attention and leaves zero executable frontier with no origin/terminal event.
- After repair, explicit `kanban_unblock` on a `blocked` or stranded `todo` terminal-affinity controller with valid pending attention atomically produces `ready`; exactly one claim succeeds and exactly one `flow_attention_requeued` exists without duplicate attention.
- Rediscovering the same pending attention requeues `todo` but never auto-promotes deliberately `blocked` before explicit recovery.
- An affinity coordinator attempting a non-`dependency` block without `origin_signal` is rejected before task/run/event mutation; its run stays in-flight for corrected handoff.
- When a non-affinity child in an affinity flow reaches an automatic terminal failure, exactly one valid direct terminal-affinity controller receives one deduplicated `flow_attention` and becomes executable despite the failed parent. If that controller is deliberately `blocked`, it is not auto-promoted without explicit recovery. If the failing card itself is terminal-affinity, existing `flow_terminal` semantics remain.
- Automatic failure routing covers `protocol_violation`/`gave_up` and representative spawn/crash/timeout circuit-breaker paths through shared kernel logic rather than duplicated per-caller patches.
- Ordinary parent-gated/non-affinity work, cards without attention, resolved attention, unrelated Projects/flows, no-controller and ambiguous graphs retain current behavior and fail closed.
- Repairable blockers remain silent to owner; unrepairable controller emits exactly one explicit signal; `flow_terminal` wakes once; cursor replay duplicates nothing.
- Same Supervisor session/workspace affinity, exclusive lease generation and single writer are preserved across both recovery paths.
- No gateway/TUI production file, new status/table/service/tool/CLI verb, provider configuration or project principle changes.
- Complete HLP-280 v2 production delta is at most 130 additions+deletions across `hermes_cli/kanban_db.py` and minimal `tools/kanban_tools.py` changes. Excess requires renewed review.
- Portable patch applies to exact captured active bytes, reverses cleanly, reconstructs candidate byte-for-byte, preserves non-targets and has recorded SHA-256.
- Before activation, active target hashes still equal the extraction baseline recorded in v1. Drift stops activation; never overwrite.
- `HERMES_LOCAL_PATCHES.md` enumerates every changed framework file/hunk/line/hash and records both v1 antecedent and v2 final behavior; index table/body/status/hotspots are consistent.
- Required local/full suites, Aether validation/build and GitHub checks pass. Any named baseline-equivalent skip must not cover either acceptance path; no new failure is accepted.
- Post-activation readback matches reviewed bytes, reload is healthy, and controlled no-watcher canaries prove both explicit recovery and automatic terminal-failure routing with bounded event counts and zero concurrent controller writers.
- If canary fails, rollback restores exact captured bytes and last-known-good canary before stop. #280 closes only after both paths are proven and evidence integrated.

## Stop Conditions

Stop and surface evidence before further mutation if:
- either deterministic RED does not reproduce on exact captured bytes;
- active target hashes drift before backup/application, another process owns a target write, or candidate provenance cannot be reconstructed;
- the complete repair exceeds 130 production additions+deletions, requires gateway/TUI production changes, a new tool/status/table/service, or broad `kanban_db.py` refactor;

- ordinary parent gating, sticky blocks, failure-limit accounting, protocol-violation enforcement, affinity fencing, Project/flow isolation or notifier deduplication regress;
- upstream gains equivalent verified implementation before integration;
- patch cannot apply/reverse/reconstruct byte-for-byte, includes another HLP's hunks, or ledger cannot attribute every framework byte;
- canonical per-file full suite has a new failure after bounded correction, or a skip covers either exact acceptance path;
- activation requires new credentials/providers/spend, unrelated service mutation or project-principle change;
- reload is unhealthy, readback differs, two writers claim controller, origin wakes more than once, repairable work wakes owner, or either explicit/automatic path leaves no executable frontier without signal/terminal event.
