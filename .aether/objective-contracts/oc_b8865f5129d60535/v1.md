# Objective Contract: Establish maintainable as-built documentation for Aether Agents

## Owner Intent

The owner wants Aether Agents to become easier to maintain, especially by formally documenting capabilities that have been implemented without a reliable current reference. The owner explicitly delegates pragmatic decisions and asks Morfeo to choose the most useful approach autonomously. The outcome must improve future maintenance rather than merely add prose or duplicate Hermes documentation.

## Objective

Establish a concise, formal and verifiable as-built documentation system for Aether Agents. Reconcile the behavior currently exposed by the package with its documentation, specifications, tests and changelog; make the authority of each documentary layer explicit; and add proportionate automated checks that prevent semantic drift of public capabilities without turning every internal change into a documentation ceremony.

## Decisions and Assumptions

Delegated decisions and supporting assumptions:

1. Add a conventional `docs/` tree and update the repository's literal manifest/policy to permit and verify it. Assumption: conventional discovery is more maintainable than creating another root-only documentation convention.
2. Keep canonical documentation in English. Conversation and handoff summaries may remain Spanish.
3. Assign one authority to each layer: `DESIGN.md` owns accepted conceptual principles/decisions; `ROADMAP.md` owns future areas and visible limitations; `specs/**/spec.md` owns normative intent; research/plans/evidence remain historical or qualification artifacts; `docs/` owns behavior available in the current build; `CHANGELOG.md` owns release deltas; `README.md` becomes a concise portal; `INTEGRATIONS.md` remains the intentional integration index.
4. Create `docs/capabilities.toml` as the sole current implementation-status and traceability registry, not as a behavioral or design authority. Use stable capability IDs and the exact statuses `implemented`, `partial`, `unsupported`, `transitional`, and `deprecated`. Each record must identify public surfaces, current documentation, owning specification when one exists, implementation paths, and verification paths.
5. Produce a deterministic human-readable capability reference from that registry, or validate an equivalent committed rendering byte-for-byte. Generated content must not become a second hand-maintained source.
6. Prioritize maintainers/operators while preserving a usable public getting-started path.
7. Keep historical specifications and evidence in place. Do not rewrite accepted history merely to resemble current behavior; label and index it instead.
8. Keep `INCOMPLETE_IMPLEMENTATIONS.md` at its existing path for compatibility, but convert it into an explicitly dated historical snapshot and remove it as an authority for current status. Active status moves to the capability registry and future work to `ROADMAP.md`/Issues.
9. Do not duplicate generic Hermes manuals. Aether documentation describes only product additions, restrictions, configured behavior, adaptations, boundaries and verified differences, and links to authoritative Hermes documentation for the rest.
10. Public/user-visible surface changes require a documentation impact update or a specific non-applicability rationale. Internal refactors and behavior-preserving fixes do not require ceremonial documentation churn.
11. Live runtime facts such as the current editable revision are observed or generated from their technical source; they are not copied manually into current documentation as durable truth.
12. No project constitutional principle changes are authorized or required. Existing owner-approved design principles remain authoritative.

## In Scope

- Inventory the current Aether-owned public surface from source, package metadata, plugins, profiles, policy and tests, including CLI commands/options, `aether_observe` actions, Objective Contract actions, project initialization, project/board/session/worktree binding, lifecycle operations, observation, role bundles, authority/policy and recovery behavior.
- Create the `docs/` architecture, index, capability registry and current reference/guides needed to cover that inventory.
- Reconcile stale or contradictory current claims across `README.md`, `AGENTS.md`, `ROADMAP.md`, `CHANGELOG.md`, `INCOMPLETE_IMPLEMENTATIONS.md`, CLI contracts and the Objective Contract specification without erasing historical evidence.
- Add a deterministic documentation validator and focused tests that derive public surfaces from their technical registries/parsers where practical, validate capability traceability and current-state consistency, and retain existing link/fence/privacy checks.
- Integrate the validator into existing CI and the literal repository manifest; update contribution and pull-request guidance proportionately.
- Slim duplicated root documentation by linking to one current authority rather than repeating status tables.
- Make only same-class documentation/tooling fixes required to complete this objective; record unrelated product defects without implementing them.

## Out of Scope

- Implementing new Aether product capabilities or changing existing runtime behavior.
- Redefining owner-approved principles, role authority, Objective Contract semantics or pipeline topology.
- Upgrading, repairing or generalizing Hermes; modifying the live editable Hermes tree; or adding a new downstream dependency.
- Activating profiles/services, invoking live providers, spending model budget, acquiring credentials, deploying, publishing a release or performing another protected external effect.
- Rewriting, deleting or relocating accepted historical specifications, research or evidence merely for tidiness.
- Building a documentation website, adding a heavy documentation framework, introducing a database/search service, or translating the canonical corpus.
- Duplicating generic Hermes user documentation.
- Broad code refactors, feature implementation, issue-backlog reconciliation or unrelated cleanup discovered during the audit.

## Authority

The owner delegated to Morfeo the pragmatic decisions needed to improve documentation maintainability. This authorizes the documented taxonomy, file naming, registry schema, current-status reconciliation, deterministic tooling, local tests, CI wiring and ordinary reversible Git/GitHub lifecycle needed for this objective in the provisioned repository. Supervisor owns decomposition, shared implementation decisions not already fixed here, convergence and integration; Implementers own bounded technical implementation within assigned worktrees; independent review must verify current-behavior claims.

This authority does not permit changing project principles, product semantics, credentials/providers, live profiles/services, the loaded Hermes runtime, deployment/public release, destructive history operations or any protected external effect. If accurate documentation exposes a product defect, document it as a finding unless it blocks this objective; do not silently fix the product.

## Deliverables

1. A documented authority model and navigable `docs/index.md`.
2. `docs/capabilities.toml` with a complete, validated inventory of the current Aether-owned surface and a deterministic human-readable capabilities reference.
3. Concise current documentation covering at minimum: product/Hermes boundary; roles and authority; installation/current lifecycle; project initialization; Objective Contracts and handoff; Projects, execution boards, session affinity and worktrees; observation; policy/recovery; CLI; plugins/tools; limitations/troubleshooting.
4. A reconciled and slimmer `README.md`; a current `CHANGELOG.md` Unreleased section; an accurate `AGENTS.md` current-versus-historical runtime boundary; and an explicitly historical `INCOMPLETE_IMPLEMENTATIONS.md` that no longer competes for current status.
5. Corrections to current reference omissions already evidenced by the audit, including `aether init` greenfield limits, `--hermes-project`, Objective Contract `validate`, and execution-board handoff behavior.
6. A lightweight standard-library documentation validator plus negative and positive regression tests, deterministic rendering/check mode, CI integration, literal manifest updates, and proportionate contribution/PR guidance.
7. A final coverage report listing every capability ID, documentation page, implementation path and verification path, plus any explicitly unresolved findings that remained out of scope.
8. Verified repository state, independent review evidence, one integrated branch/PR as appropriate, and no leaked local runtime data or private paths.

## Acceptance Criteria

- A maintainer can start at `README.md`/`docs/index.md` and determine, without reading source, what Aether currently implements, what is partial/unsupported/transitional, where the normative intent lives, and how each implemented capability is verified.
- The capability registry has unique stable IDs, only the five approved statuses, valid project-relative paths, and complete coverage of Aether-owned CLI commands/relevant public options, package plugin entry points, registered Aether tools/actions, portable role resources and documented policy/lifecycle surfaces.
- Every `implemented`, `partial` or `transitional` capability links to at least one current document, implementation path and verification path. Every `unsupported` or `deprecated` capability has an honest current explanation and no false ready claim.
- The validator derives registrable surfaces from code/package registries where practical and fails on fixtures for a missing command/action, an invalid/missing path, an unknown status, duplicate IDs, a stale generated reference and implemented capability without verification.
- Existing Markdown link/fence/privacy and canonical-manifest checks continue to pass after `docs/` is intentionally admitted.
- The known contradictions from the baseline audit are resolved: implemented `init` is not described as unsupported; current greenfield behavior is truthful; `--hermes-project` and Objective Contract `validate` are documented; contract-version execution-board isolation is documented; Unreleased includes the material user-visible additions; live editable revisions are not presented as durable current truth.
- `README.md` is a portal rather than a second full status/design manual. `INCOMPLETE_IMPLEMENTATIONS.md` visibly identifies itself as historical and points to current authorities. Historical specs/research/evidence remain available and are not rewritten as current behavior.
- Current Aether pages link to upstream Hermes for generic functionality and contain no copied generic manual or operator-specific runtime state.
- The deterministic no-provider test standard passes, the full existing test bootstrap remains green, the package builds, the diff is clean, and independent review finds no material undocumented Aether-owned public capability or competing current authority.
- Any out-of-scope defect discovered is reported explicitly with evidence and is not silently fixed.

## Testing Standard

Testing is deterministic, local, provider-free and evidence-based.

Required focused checks:
- validator check/render idempotence (`uv run --frozen python scripts/check_documentation.py`, with the exact implemented check mode documented);
- positive and negative documentation-contract tests, including public-surface extraction and stale rendering fixtures;
- `uv run --frozen pytest -q tests/test_public_artifacts.py tests/test_hermes_baseline.py` plus the new documentation tests;
- focused existing suites for every reconciled surface, including project initialization, Objective Contracts, observation CLI/plugin and policy/launcher behavior when those files are touched;
- Markdown local-link/fence/privacy and literal-manifest validation.

Required repository gates before handoff:
- `uv run --frozen ruff check src/aether_agents tests scripts`;
- `uv run --frozen ruff format --check src/aether_agents tests scripts`;
- `uv run --frozen mypy src/aether_agents` when Python source/typed tooling changes;
- `uv run --frozen python scripts/run_tests.py` using the repository's locked exact-Hermes bootstrap;
- `uv build`;
- `git diff --check`, clean intended status, and inspection of the complete diff.

Documentation examples that claim executable behavior must be exercised against the local build or generated from the actual parser/registry. No live model/provider, credentials, service activation, deployment or public publication is part of acceptance. Independent review must sample the registry against source and tests rather than trusting generated output alone. The baseline audit passed the existing documentation checks (16 tests), so acceptance requires new negative regressions that would have caught the observed semantic contradictions.

## Stop Conditions

Stop and escalate rather than infer if:
- accurate documentation would require changing an owner-approved principle, product behavior, authority boundary or Objective Contract semantics;
- project identity, portable marker, prepared execution board or exact path-matched Hermes Project becomes missing, ambiguous, archived or conflicting;
- the requested outcome would require modifying the live editable Hermes runtime, acquiring credentials, invoking a live provider, deploying, publishing or another protected effect;
- a current-behavior claim cannot be resolved from repository source/tests and accessible authoritative upstream documentation;
- the capability registry starts becoming a second behavioral specification, runtime dependency or generalized product framework rather than a documentation traceability manifest;
- historical evidence would need to be deleted or rewritten to make validation pass;
- the full suite exposes a product defect outside documentation/tooling that does not block this objective. Record it separately instead of absorbing it.

If a same-class documentation validator or manifest defect blocks acceptance, make only the smallest verified repair. If the implementation expands into product architecture or a third repair variant without advancing the objective, stop and report the blocker.
