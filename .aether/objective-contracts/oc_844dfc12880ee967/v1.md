# Objective Contract: Convertir la documentación web de Aether Agents en una guía completa para principiantes

## Owner Intent

The owner authorizes autonomous work on the Aether Agents public website, with broad permission to change any website element needed for this documentation objective. The desired outcome is documentation that teaches a human with no prior Aether Agents knowledge how to understand and use the product. The owner will be unavailable during execution and requests well-written progress updates through the already provisioned Telegram channel. This instruction authorizes documentation and website changes necessary for the objective plus ordinary repository closeout under existing credentials and required checks; it does not authorize credential changes, provider calls, deployment, release publication, repository-setting changes, bypass, destructive cleanup, or modification of unrelated product/runtime behavior.

## Objective

Create a coherent, beginner-first documentation experience for the Aether Agents website that takes a reader from zero context to an accurate mental model, safe local orientation, eligible project initialization, choosing direct work versus the pipeline, forming an Objective Contract when required, following execution/review/evidence, and diagnosing current limitations. Reconcile the canonical docs corpus and its website presentation so the journey is discoverable, navigable, truthful to the current repository, and usable on desktop and mobile without implying that the stabilization build is a public release or a complete installation path.

## Decisions and Assumptions

Decisions:
1. The primary reader is a technically capable human who can use Git and a terminal but has zero Aether-specific context. The documentation explains Aether concepts, prerequisites, commands, expected outcomes, decisions and failure boundaries; it does not become a general Git/Python tutorial.
2. Keep the tracked `docs/` corpus as the single canonical technical manual and render it directly in the website. Canonical pages remain English under the existing website language policy; the Spanish-Mexican website entry/orientation may summarize and route into them. No automatic or duplicated full translation is introduced.
3. Reframe navigation as a learning journey with explicit groups: Start here, Core concepts, Working with Aether, Operations/safety, and Reference. Deep reference remains available but no longer substitutes for onboarding.
4. Add a canonical beginner pathway, including a concise glossary and one clearly labeled end-to-end first-objective walkthrough that distinguishes an example from requirements and labels what is runnable in the current build versus conceptual/intended workflow.
5. Preserve status truth from code, tests and `docs/capabilities.toml`: the provider-free source-checkout path is the only guaranteed beginner exercise. Interactive/provider-backed/public installation behavior must be described as limited or unqualified where current evidence says so.
6. Improve the docs UI where needed: grouped navigation, visible current location, useful in-page headings, pedagogical previous/next order, mobile navigation, search orientation, readable code/tables and accessible deep links. Exact component/CSS structure is local implementation freedom.
7. Update existing pages and cross-links rather than copying large explanations into every page. Reference material stays precise; beginner pages explain why and when, then link to details.
8. Local commits, a normal branch push, PR creation and required checks are authorized under the owner's unattended-work request and standing project closeout policy. Merge is deferred because this repository's `main` push triggers the GitHub Pages deploy job; without separate deployment authority, a merge is not an ordinary non-deploying closeout step.
9. Release conclusions are independent: `release_impact = patch` because this is a backward-compatible correction/expansion of documentation and its reading surface without changing Aether runtime/API contracts; `release_action = defer`; `release_channel = none`. A PR or eventual merge does not change those conclusions by itself.
Assumptions supporting these decisions: the owner's request targets comprehension and use, not a language translation project; existing website policy explicitly keeps the canonical manual English; project design identifies the intended user as a working programmer; the current capability registry and guides explicitly deny release/public-install readiness; permission to change website content does not silently widen into permission for an external deployment.

- Rework `docs/index.md` into a beginner-first map while preserving authority/status routing.
- Expand or complement `docs/getting-started.md` with an explicit learning path, prerequisite explanations, provider-free inspection steps, expected observations and honest next steps.
- Add canonical beginner content for the product mental model, lifecycle/route choice, a complete first-objective walkthrough, evidence/review/stop behavior, and a glossary when these are not already sufficient. New pages must be included in navigation/search/source linking and be non-duplicative.
- Reconcile role, authority, project initialization, Objective Contract, execution, lifecycle, knowledge, observation, policy/recovery, CLI, tools, capability and troubleshooting pages enough to make the journey coherent and technically current.
- Refactor the website documentation metadata/information architecture so grouping and pedagogical order are explicit and stable for existing and new pages; remove fragile implicit ordering.
- Improve `/docs/` and individual `/docs/**` pages, shared navigation and documentation styles/components for beginner orientation, grouped discovery, current-location cues, heading navigation, adjacent-page flow, desktop/mobile accessibility, code/table readability, search and no-JavaScript content access.
- Add/update content, unit and browser tests plus any focused verification utility needed to validate corpus completeness, local links/fragments, generated routes, source links, grouped order, search/navigation, accessibility and responsive/no-JavaScript behavior.
- Validate documented commands and status claims against the checked-out code, parser help, tests, `docs/capabilities.toml`, canonical design/specifications and authoritative Hermes docs when generic Hermes behavior is referenced.
- Update website operating/verification documentation if the implemented structure or required commands make it stale.
- Reconcile GitHub issue #368 and perform authorized GitHub-backed closeout through an independently reviewed PR with required checks green; do not merge while that action triggers an unauthorized Pages deployment.
- Configure well-written, change-driven Telegram progress reporting for this objective using the already provisioned destination; reports must distinguish observed board state from inference and stop after terminal outcome.

## Out of Scope

- Implementing missing Aether product/runtime capabilities merely to make the documentation's ideal journey executable.
- Claiming, preparing or publishing a stable/prerelease package, installer, hosted service, release candidate, deployment, domain change, analytics or production activation.
- Invoking live model providers, creating/widening credentials, changing provider/model/router bindings, or copying local profile/runtime state into public content.
- Teaching generic Hermes installation, account/provider setup or credential management beyond concise context and links to the current authoritative Hermes Agent documentation.
- A complete Spanish translation of the canonical English technical corpus, localization infrastructure, or translation maintenance system.
- Redesigning the approved landing-page identity, headlines, artwork or decorative motion unless a narrow change is required to make documentation discovery and entry coherent.
- Changing product architecture, role authority, lifecycle policy, Objective Contract semantics, Kanban behavior, knowledge tools, CLI behavior or test policy.
- Editing historical specs as though they were current reader documentation, rewriting unrelated planning archives, or presenting examples as new requirements.
- Resolving unrelated defects discovered during the work. Record/reconcile them through a separate issue when project policy requires it; a same-class blocking documentation defect may receive only the smallest verified correction.
- Bypassing checks, mutating repository settings, force-pushing/rewriting history, destructive cleanup, or deleting active/concurrent work.
- Merging to `main`, deploying the website or publishing a release under this authority. A green reviewed PR is the authorized terminal repository state and is not evidence of live publication.

If accurate beginner instruction requires an unresolved product decision or an unimplemented capability, document the honest boundary and escalate a contract revision rather than inventing behavior.

2. A reworked website documentation landing/index that tells a zero-context reader where to start, what they will learn, which content is current/runnable, and how to proceed through the manual.
3. Grouped, pedagogically ordered documentation navigation shared across index and article pages, with visible current position, mobile behavior, adjacent-page journey and stable handling of every tracked canonical page.
4. Useful in-page orientation for long documents (heading/table-of-contents or equivalent), accessible anchored headings, readable code/tables and source-revision links.

6. Automated content/link/fragment/route/source-integrity tests and browser tests covering desktop/mobile docs navigation, search, accessibility, responsive overflow, keyboard use and no-JavaScript essential reading.
7. Executed verification evidence for website gates and relevant repository documentation/status checks, including actual command outputs, known limitations and an independent review that was not authored by the implementing worker.
8. Updated website guidance/verification notes when required by the resulting architecture, with no stale claim that contradicts the implemented docs surface.
9. A normal GitHub PR linked to issue #368 with required checks green and objective-caused failures resolved without bypass. Merge, issue closure through merge, Pages deployment and release publication remain pending separate deployment authority.
10. Change-driven Telegram progress briefs for meaningful pipeline milestones and a terminal summary, sent to the owner's existing Telegram destination without exposing private paths, tokens, logs or opaque routing data.

## Acceptance Criteria

1. `/docs/` presents an unmistakable start point and a sequenced learning journey. Without reading repository internals, a zero-context technical reader can identify what Aether is, what it is not, who the owner/Morfeo/Supervisor/Implementer are, and why direct and pipeline routes both exist.
2. The beginner path states prerequisites before commands, explains each Aether-specific term on first use or links it to a glossary, provides expected observations/interpretation, and ends each major page with a concrete next step.
3. A complete, clearly labeled example follows one owner-authorized objective from intake through route selection, contract use when applicable, board/worktree execution, review/evidence, GitHub-backed closeout and terminal reporting. It also contrasts a bounded direct example. The example does not create new normative requirements or claim that provider-backed execution was run.
4. The docs explicitly and consistently distinguish current implemented behavior, partial/transitional/unsupported behavior, intended design, and historical evidence. They state that the repository is a stabilization build, public installation/interactive launch/release qualification is incomplete, and provider-free source inspection is the safe runnable entry path.
5. Every user-facing command, option and expected success/non-success condition in the beginner path is checked against the current parser/code and executed provider-free where safe. Generic Hermes setup/configuration is linked to authoritative Hermes documentation and not restated from memory.
6. Every tracked canonical `docs/**/*.md` page is represented once in generated website routes, grouped metadata, navigation and search, or is deliberately excluded by an explicit tested rule. Adding an unknown tracked page cannot silently place it before the learning journey or omit it without a failing test.
7. All internal documentation links and local fragments resolve in both source-relative and generated website routing semantics. External/source links use safe schemes; repository source links remain revision-pinned. Broken anchors, duplicate heading IDs and missing generated routes fail verification.
8. On individual docs pages, desktop and mobile users can identify the document group/current page, search or return to the docs index, navigate the document's headings, and proceed to the next/previous pedagogical page. Keyboard focus and current-page semantics are correct. Loading a URL with a valid heading fragment visibly positions the target below the sticky header rather than merely resolving an existing ID.
9. Search finds content by document title, description and body, supports representative beginner terms in Spanish orientation and canonical English terminology, reports result count/no-result state, and is available from article context or through an equally prominent route. With JavaScript unavailable, the complete index/navigation remains usable and an inert search control is hidden or clearly marked unavailable.
10. At desktop and the configured mobile viewport, docs pages have no unintended horizontal page overflow; long code and tables scroll within their own accessible regions. Essential content, heading navigation and route navigation remain readable with JavaScript disabled.
11. Automated accessibility checks report no WCAG A/AA violations on the docs index, start page, walkthrough, a long reference page and a representative mobile rendering. Heading hierarchy, landmarks, language metadata, focus and accessible navigation names are checked.
12. Public artifacts contain no credentials, private runtime/profile state, owner contact/channel identifiers, machine-specific paths, sessions, boards, logs, provider/model bindings or opaque routing data. The Telegram reporting mechanism remains local operational state and is not committed.
13. `website/AGENTS.md`, documentation metadata/descriptions and verification notes accurately describe the resulting implementation and commands. Historical design/proposal files remain historical unless a narrowly necessary status correction is made.
14. The implementation is independently reviewed against this contract, relevant tests pass without weakening existing gates, issue #368 and the PR are linked, and required PR checks succeed without bypass. Because merge would trigger GitHub Pages deployment, merge and issue closure remain pending separate owner deployment authority; the final report states that boundary and does not imply live publication.

## Testing Standard

Testing is provider-free, evidence-based and proportional to a documentation-plus-Astro UI change. Implementers use test-first regression where feasible: add focused failing tests for each new invariant (beginner route, explicit grouping/order, corpus completeness, fragments, navigation/TOC/search behavior) before or with the corresponding implementation, then preserve existing coverage without weakening assertions, skipping failures or replacing semantic checks with snapshots.

Start from a clean generated-artifact state; stale ignored `website/dist`, `.astro`, Playwright reports or prior captures are not evidence. From `website/`, run `npm ci`, then:
- `npm run build`
- `npm run check`
- `npm test`
- `npm run test:e2e`
- `AETHER_PAGES=1 npm run build`
- `node scripts/verify-pages-build.mjs`
- rebuild the normal non-Pages output after the Pages check if further local/browser inspection follows;
- `node scripts/capture.mjs` when docs layout/style changes affect responsive rendering; inspect representative desktop/mobile docs captures, not only exit status.

Required project-root gates:
- `uv run --frozen python scripts/check_documentation.py`
- `uv run --frozen pytest -q tests/test_documentation.py tests/test_public_artifacts.py`
- provider-free parser probes for every beginner-facing command (`uv run --frozen aether --version`, `uv run --frozen aether --help`, `uv run --frozen aether observe --help`, and any additional documented command/help path) in an isolated temporary HOME with `HERMES_HOME` unset; record both exit code and interpretation. A read-only `doctor` nonzero or ambiguous `observe` result may be the documented expected result and must not be normalized into success.
- `git diff --check`
- relevant policy/documentation checks selected from the actual changed paths and current workflow; no full Python suite is required for docs/website-only changes unless implementation touches Python/runtime behavior or a focused check exposes a regression that makes the broader suite material.

Automated content verification must enumerate the tracked public `docs/**/*.md` corpus and assert metadata/route/search/navigation coverage, unique slugs/heading IDs, valid source-relative and generated internal links/fragments, safe URL schemes, revision-pinned source links and no private/untracked ingestion. It must fail on an unclassified new document instead of silently sorting it first or omitting it.

Browser verification runs at least the configured desktop and mobile projects and covers: the docs index, beginner start page, first-objective walkthrough, one long reference page, grouped/current navigation, in-page headings, direct URL fragment loading and visible target positioning below the sticky header, previous/next order, search success/no-result/degraded behavior, keyboard focus, language metadata, no unintended page overflow, local scroll regions for code/tables, no-JavaScript essential content/navigation, and automated WCAG A/AA checks. Any visual review limitation is stated honestly.

Supervisor must obtain an independent review from a reviewer who did not author the implementation, reconcile all actionable findings, then verify the integrated branch and PR checks. Passing local tests is not evidence of Pages deployment or release. Expected test effects: existing documentation count/order assertions change only to reflect the new canonical manifest/pages; landing-page copy/artwork/motion regressions remain green; new semantic tests fail against the baseline and pass only after the beginner journey/UI exists.

## Stop Conditions

Stop and return a structured blocker/contract-revision request if any of the following occurs:
- The bound portable project, native Project, execution board, repository remote/default branch or base revision becomes missing, ambiguous or conflicting.
- Current source, `docs/capabilities.toml`, design/specification authority and existing reader docs conflict in a way that materially changes what the beginner is allowed to do and cannot be resolved by labeling intended versus implemented behavior.
- A required accurate onboarding step depends on a missing product capability, credential/provider invocation, unqualified installation path or owner-only product decision. Document the boundary where possible; do not implement the capability under this objective.
- Work would require deployment, merge-to-main while Pages deployment remains coupled, release/package publication, repository-setting mutation, credential acquisition/widening, provider/model/router changes, bypass, history rewrite or destructive cleanup.
- A genuine protected-edge denial occurs. Do not route around it.
- Independent review identifies a material truthfulness, safety, navigation or accessibility defect that cannot be corrected within this documentation/website scope.
- Required local tests or PR checks fail for an objective-caused reason after bounded diagnosis and correction, or the current baseline is demonstrably red in a way that prevents attribution. Preserve evidence and do not weaken tests.
- Source integration would overwrite or absorb active concurrent work. Rebase/reconcile safely where authorized; otherwise stop with the collision evidence.
- Public content would need private runtime state, real credentials, personal contact/channel identifiers, machine paths or unverifiable live claims to appear complete.

Do not stop merely because the owner is unavailable, prose needs iterative refinement, an implementer needs ordinary local judgement, or a recoverable test issue has a bounded in-scope fix. The authorized terminal state is a reviewed PR with green required checks and explicit merge/deployment deferral, not a live Pages deployment.
