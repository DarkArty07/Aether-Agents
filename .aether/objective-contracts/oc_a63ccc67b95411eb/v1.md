# Objective Contract: Formalize autonomous Git/GitHub project stewardship and canonical skill governance

## Owner Intent

Christopher wants Aether to maintain an authorized Git/GitHub project from objective intake through verified repository closure without requiring separate instructions for commits, push, pull request, checks, merge, cleanup, issue reconciliation, release-impact classification, SemVer, or a GitHub Release when the project's standing release policy calls for one. Preserve the three-role architecture rather than adding a lifecycle agent. Formalize Aether-owned and project-owned canonical skills as versioned, reviewed procedures distinct from private skills learned by Hermes profiles. Every Aether project must have accurate root `AGENTS.md` guidance: Morfeo establishes it when absent, the agent whose change invalidates it updates it, and Supervisor verifies it before closure. This objective must retain every agreed boundary and add coherence rather than a new workflow framework.

## Objective

Make the already accepted end-to-end stewardship promise in `DESIGN.md` PD-15 and the routine GitHub publication authority in R8 FR-824 coherent, executable, testable, and discoverable across Aether's canonical specifications, all three packaged role SOULs, current documentation, repository guidance, release automation, and a minimal set of Aether-owned canonical skill resources. Define one terminal completion contract for direct and pipeline work so local integration alone is never reported as project closure. Define canonical project skills and learned profile skills without creating a second authority source, skill engine, agent role, queue, or release framework.

## Decisions and Assumptions

Accepted decisions and supporting assumptions:
1. Aether owns the lifecycle as a system; no fourth role is added. This preserves PD-13/PD-30/PD-33 and assumes lifecycle closure is a responsibility alignment problem, not an absent agent identity.
2. Autonomy begins after one owner-authorized objective and operates within the project's established constitution, repository guidance, release policy, existing GitHub remote and already-provisioned credentials. Aether never invents objectives or acquires/widens access.
3. When project policy uses GitHub Issues and the authorized objective is not already represented, Morfeo creates or reconciles one non-duplicate issue at intake; issue creation is not mandatory ceremony for every objective. The mandatory closeout sequence for a GitHub-backed objective is: acceptance verification; aggregate compatibility/release decision; normal branch push; PR; required checks; bounded diagnosis/correction of objective-caused CI failures; green merge without bypass; issue/milestone reconciliation when applicable; remote merged-branch cleanup; local objective branch/worktree cleanup after terminal evidence is durable; final evidence report. Every omitted step carries an explicit non-applicability reason.
4. Every objective produces three separate conclusions: `release_impact = none|patch|minor|major`; `release_action = defer|prepare|publish`; and `release_channel = none|prerelease|stable`. These are semantic report obligations, not permission to invent a second state machine or registry. Prerelease is a publication channel, never a compatibility-impact class.
5. SemVer impact classification is autonomous when the project's compatibility contract settles it. A material ambiguity about public compatibility returns through Morfeo to the owner. Release action/channel follow the standing project release policy; not every merge implies a release.
6. For pipeline work, Supervisor owns GitHub publication after independent review, as R8 FR-824 already requires. Implementer may prepare version/changelog/artifacts in an assigned unit but never publishes. For direct work, Morfeo completes routine GitHub closure only within current or standing project authority.
7. Aether `v1.0.0` stable publication retains its explicit owner gate under A1-FR-089/R13 FR-1350. This objective does not waive release qualification, credentials, model-spend, package publication, deployment, migration, or destructive-effect gates.
8. Canonical skills have procedural authority only and remain subordinate to current owner instruction, constitution, `DESIGN.md`, stage specs, Objective Contracts, and repository operating rules. A skill cannot grant authority or redefine intent/acceptance.
9. Three skill classes are normative: Aether Canonical Skills (public/versioned/package-owned); Project Canonical Skills (tracked/versioned/portable under that project's own visibility); Learned Profile Skills (private/local/adaptive and non-canonical). Learned skills never auto-promote; promotion requires sanitization, generalization, verification, independent review, commit and PR.
10. Aether Canonical Skills live under `src/aether_agents/resources/skills/<skill-name>/SKILL.md`. Project Canonical Skills live under `.aether/skills/<skill-name>/SKILL.md`. Directory contents and SKILL.md frontmatter are the source; do not add a duplicate registry unless implementation proves one necessary. `AGENTS.md` points any agent to project skills, while each SOUL defines discovery/precedence without enumerating a stale skill list.
11. Initial Aether Canonical Skills cover: Git/GitHub project closeout; SemVer/release decision and execution; canonical-skill governance/promotion. Keep them focused and non-overlapping rather than creating a routing/index skill.
12. Every Aether project has root `AGENTS.md`. Morfeo establishes it from observed greenfield/brownfield reality when absent; existing brownfield instructions are preserved and reconciled, never overwritten generically. The agent whose authorized change invalidates an operating instruction updates it in the same change. Supervisor owns the final coherence gate. Nested `AGENTS.md` files are introduced only for demonstrated subtree-specific rules.
13. The three SOULs reference the canonical-skill concept and load only task-relevant skills. Supervisor pins or names applicable skills in cards; Implementer may not replace a canonical project procedure silently with a learned skill.
14. Preserve evidence in Git, PR and board rather than retaining completed worktrees indefinitely. The current R8 branch-preservation wording must be reconciled with FR-824 cleanup: preserve through review/integration/publication, then remove merged objective residues once durable evidence exists.
15. Use existing Hermes file/skill/card/worktree/review mechanisms and GitHub Actions. No new generic skill loader is authorized. Minimal Aether-owned packaging/materialization wiring is permitted only if an existing public extension/configuration path already supports it; otherwise stop for revision rather than modifying Hermes core.
16. Owner decision for PD-74: this exact objective is authorized as bounded alignment of accepted PD-15/FR-824 plus canonical procedural governance. It does not lift the reliability freeze for unrelated features. If implementation requires a new runtime engine or broader feature expansion, stop.
17. Assumption supporting the GitHub boundary: the requested coherence applies to already provisioned Git/GitHub projects. Automatic remote repository creation, repository settings mutation, package registry publication, deployment and scheduled unattended maintenance remain outside this objective. Owner-authorized maintenance or retirement objectives use the same closeout rules, but Aether does not schedule them here.

AC18. Aether's `v1.0.0` stable publication remains blocked on its existing explicit owner and qualification gates despite generic routine GitHub autonomy.

AC20. Current documentation states model coverage separately from implemented/qualified capability. `docs/capabilities.toml` does not label any path implemented without source and focused verification.
AC21. No fourth role, Hermes core patch, new workflow/skill engine, daemon, scheduler, credential change, remote-repository creation/settings mutation, package publication, deployment, migration or unrelated feature appears in the diff.
AC22. Existing Aether behavior, documentation validation, public artifact boundaries, objective-contract functionality, profile packaging and policy tests remain green.
AC23. The contract's own final candidate is pushed, opened as a PR, passes required checks, merges normally, deletes its remote branch, reconciles a linked issue or records why none applies, and leaves no objective-owned local worktree/branch/stash residue after final notification.
AC24. The final report is built from durable board, Git and GitHub state and identifies the three release conclusions, exact merge, checks, issue disposition, cleanup, remaining pre-existing residues and every acceptance limitation without asking Christopher to operate the repository.
