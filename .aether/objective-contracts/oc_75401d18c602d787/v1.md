# Objective Contract: Clarify Aether documentation architecture and artifact ownership

## Owner Intent

Christopher wants Aether's documentation architecture clarified before defining or evaluating what Aether should do autonomously. A reader or agent must be able to determine where each kind of information belongs, which artifact owns it, what it does not own, and how conflicts are resolved. Only after this foundation is complete will Christopher and Morfeo jointly define Aether's mission, high-level capabilities, autonomy envelopes, and use cases.

## Objective

Establish a coherent, navigable, non-duplicative documentation architecture for Aether Agents. Define the semantic levels and authoritative placement rules for framework-wide, role-specific, user-private, environment-specific, project-specific, objective-specific, execution, evidence, history, and current-status information. Reconcile the canonical artifact relationship with the reader-facing documentation map so future mission and capability work has one unambiguous home.

## Decisions and Assumptions

Decisions: (1) `DESIGN.md` section 13 remains the normative owner of canonical artifact relationships; this objective must refine it rather than create a competing authority. (2) `docs/authority.md` is the complete reader-facing explanation of where information belongs and how to resolve conflicts. (3) `docs/index.md` is navigation only. (4) `AGENTS.md` retains checkout-specific instructions and may link to the map but must not duplicate product truth. (5) Private user/profile/memory content and machine paths remain outside public artifacts; public docs describe only their artifact classes and boundaries. (6) Prefer updating existing artifacts; add a new document only if evidence demonstrates that the existing ownership split cannot remain clear. Assumptions: the current artifact authority declared in `DESIGN.md` and `docs/authority.md` remains owner-approved; this phase changes documentation structure and clarity, not product behavior or autonomous capability promises.

## In Scope

Inspect the current canonical and public documentation relationships; define a complete artifact taxonomy and placement rule; distinguish current owner instruction, project constitution, product design, stage requirements, rationale/research, role identity, private user preference, private environment memory, reusable skills, checkout instructions, objective contracts, execution coordination, current behavior docs, capability status, roadmap/issues, release history, verification evidence, and effective runtime state; define precedence and conflict-resolution flow; reconcile `DESIGN.md` section 13, `docs/authority.md`, `docs/index.md`, and only materially affected navigation or contributor guidance; preserve public/private and portable/local boundaries; independently review the resulting map for duplicate ownership and misleading authority.

## Out of Scope

Do not define or approve Aether's mission, high-level product capabilities, autonomy envelopes, use cases, or ten-discipline capability coverage in this phase. Do not change agent behavior, SOUL content, private USER/MEMORY content, skills, runtime configuration, policies, source code, capability implementation status, release scope, project principles, or authority boundaries. Do not publish private paths, owner-specific data, credentials, models, providers, or live runtime facts. Do not repair unrelated stale documentation unless it directly prevents a coherent artifact map; record such findings instead.

## Authority

Authorized: inspect and edit repository documentation and documentation-validation fixtures or allowlists only as required by the accepted documentation architecture; use normal reversible Git/worktree operations; run local documentation, policy, syntax, and link checks; create a reviewable branch/commit and follow the owner-preauthorized routine GitHub lifecycle after independent review. Not authorized: changing product intent, project principles, role behavior, private profile/memory state, source/runtime behavior, credentials, providers, spending, services, deployment, publication of packages, destructive Git operations, bypasses, or unrelated cleanup. Any newly discovered ambiguity that would assign product mission or autonomous capability authority must return to Christopher rather than be decided in this objective.

## Deliverables

1. A refined normative artifact-relationship section in `DESIGN.md` that assigns each semantic information class to exactly one authoritative artifact class and distinguishes derived context/evidence. 2. A complete reader-facing `docs/authority.md` map with scope, ownership, non-ownership, public/private boundary, placement guidance, and conflict resolution. 3. Updated `docs/index.md` navigation that lets readers find the correct authority by question. 4. Only necessary cross-links in existing repository guidance; no duplicate manual. 5. Independent review findings resolved. 6. A concise verification record listing checks executed, affected files, any explicitly deferred inconsistencies, and confirmation that mission/capability/use-case definition remains the next owner collaboration.

## Acceptance Criteria

AC1. The documentation classifies at least framework-wide, role-specific, user-private, environment-specific, project-specific, objective-specific, execution, evidence, history, and current-status information. AC2. Every listed information class has one authoritative artifact class, explicit non-ownership, scope/portability, and a safe placement rule. AC3. The map distinctly covers current owner instruction, constitution, `DESIGN.md`, specs, research, SOUL, private USER/MEMORY, skills, `AGENTS.md`, Objective Contracts, boards/tasks/worktrees, current docs, `capabilities.toml`, roadmap/issues, changelog/releases, Git/PR/tests, and runtime state. AC4. Normative relationships remain in `DESIGN.md`; `docs/authority.md` explains without competing; `docs/index.md` navigates without restating. AC5. Conflict resolution updates the artifact that owns the question before derived artifacts and preserves evidence/history. AC6. No private content, machine-specific path, owner identifier, credential, model/provider binding, or live runtime claim is introduced. AC7. No mission, product-capability, autonomy, or use-case decision is made or implied. AC8. All affected links and repository documentation/policy checks pass. AC9. Independent review finds no duplicate authority, circular ownership, false current-status claim, or hidden expansion of scope. AC10. The final handoff identifies the exact next design boundary: joint owner/Morfeo definition of mission, capabilities, autonomy and use cases.

## Testing Standard

Documentation-only standard: run `uv run --frozen python scripts/check_documentation.py`; run `uv run --frozen python scripts/run_tests.py` to detect repository-policy regressions; run any additional policy/public-artifact check that the changed manifest or documentation paths trigger; run `git diff --check`, inspect the complete diff and validate every added or changed relative link. Require an independent reviewer to test the ownership map against representative placement and conflict scenarios, including private-versus-public and portable-versus-local cases. No provider-backed, live runtime, deployment, E2E, or spend-bearing test is applicable because executable behavior and runtime state are out of scope; if implementation expands into either, stop and revise the contract before continuing.

## Stop Conditions

Stop and return for owner decision if the work requires redefining Aether's mission, high-level capabilities, autonomy, project principles, role responsibilities, authority boundaries, public/private product boundary, or current capability status. Stop if two accepted normative artifacts claim irreconcilable ownership, if private runtime/user data would need publication, or if a documentation-only change cannot pass the existing repository policy without changing executable behavior. Record non-blocking stale or unrelated findings without repairing them. Completion occurs only after the canonical map, reader guide, navigation, checks, and independent review all agree.
